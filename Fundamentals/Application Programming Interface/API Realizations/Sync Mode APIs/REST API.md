**RESTful API** — это API поверх HTTP/1.1, разработанный согласно правилам **REST**.

**REST (Representational State Transfer)** — это **архитектурный стиль взаимодействия компонентов распределённого приложения в сети**. Не протокол, не стандарт, а **набор рекомендаций** (RESTfu - прилагательное). Его придумал Рой Филдинг в 2000 г., он опирается на 6 принципов. Они помогают создавать гибкие, масштабируемые и простые в поддержке веб-сервисы:

Клиент-серверная архитектура, stateless, кеширование, единообразие интерфейса, уровни, возможность выполнения кода.

- **Клиент-серверная архитектура.** REST API подразумевает чёткое разделение между клиентом и сервером. Клиент запрашивает данные, а сервер их предоставляет. Такое разделение улучшает масштабируемость системы и позволяет клиентам работать независимо от серверной логики.
- **Отсутствие состояния (stateless).** Каждый запрос от клиента к серверу обрабатывается независимо от предыдущих запросов. Сервер не хранит информацию о состоянии клиента, что упрощает обработку запросов и повышает отказоустойчивость системы.
- **Кеширование.** Ответы сервера могут кешироваться, чтобы снизить нагрузку на сервер и ускорить загрузку данных. REST API поддерживает механизмы кеширования, такие как HTTP-заголовки Cache-Control и ETag, которые позволяют клиентам повторно использовать ранее полученные данные.
- **Единообразие интерфейса.** Все ресурсы REST API должны иметь чёткую структуру и единообразные URL-адреса. Запросы к API выполняются с использованием стандартных методов HTTP, а данные передаются в предсказуемых форматах, таких как JSON или XML.
- **Система уровней (Layered System).** REST API может включать несколько уровней, таких как балансировщики нагрузки, прокси-серверы и системы аутентификации. Каждый уровень выполняет свою функцию и не зависит от других, что повышает надёжность и гибкость системы.
- **Возможность выполнения кода по требованию.** Хотя этот принцип не является обязательным, REST API может поддерживать загрузку и выполнение кода на стороне клиента, например в виде скриптов или небольших программ.

## Ключевые компоненты REST API

1. **Ресурсы (Resources)**. Ресурс — это любая сущность, к которой можно получить доступ через API. Это могут быть пользователи, заказы, товары или любые другие объекты системы. Каждый ресурс имеет уникальный идентификатор (URI)
2. **Методы HTTP**. Для взаимодействия с ресурсами используются стандартные методы HTTP
3. **Запросы и ответы**. Обмен данными между клиентом и сервером происходит через HTTP-запросы и ответы. В большинстве случаев используется формат JSON, поскольку он удобен для чтения и поддерживается большинством языков программирования
4. **Заголовки HTTP**. Заголовки используются для передачи дополнительной информации, такой как тип контента (Content-Type), параметры аутентификации (Authorization), кодировки и кеширования (Cache-Control)
5. **Коды ответа HTTP**. Каждый HTTP-запрос получает ответ с определённым кодом состояния

**Работа с HTTP‑протоколом:**

1. Используйте HTTP‑методы (GET, POST, PUT, DELETE, PATCH) корректно — например, не применяйте GET для удаления ресурса.
2. Возвращайте статус‑коды, отражающие реальный результат запроса (2xx — успех, 3xx — редиректы, 4xx — ошибки клиента, 5xx — ошибки сервера).
3. Учитывайте идемпотентность операций: повторное выполнение не меняет состояние системы после первого запроса (например, метод DELETE).

**Нейминг и формирование URL:**

4. Применяйте множественное число в названиях ресурсов (например, `/users`, а не `/user`).
5. Избегайте глаголов в названиях — HTTP‑методы уже описывают действие.
6. Используйте иерархические отношения ресурсов в URL, чтобы явно указывать связи между ними (например, `/products/123/reviews/456`).
7. Добавляйте query‑параметры для фильтрации и сортировки данных (например, `/products?category=electronics&sort=price`).
8. Указывайте единицы измерения и используйте стандарты (например, ISO 8601 для дат).

**Дизайн API:**

9. Ориентируйтесь на потребности клиентов, а не на внутреннюю структуру системы — используйте понятную клиентам терминологию.
10. Внедряйте версионирование API, чтобы избежать поломок при несовместимых изменениях (например, `/v1/products` и `/v2/products`).
11. Предоставляйте возможности фильтрации, сортировки и пейджинга (разбиения больших коллекций на страницы).
12. Формулируйте осмысленные сообщения об ошибках (например, «Product not found» вместо «Error: something went wrong»).
13. Настраивайте кэширование для часто запрашиваемых или статических данных, чтобы снизить нагрузку на систему.
14. Реализуйте хелс‑чек‑эндпоинт (например, `GET /health`), чтобы сообщать о состоянии API.

**Инфраструктура:**

15. Ограничивайте частоту запросов (рейт‑лимитинг) и контролируйте нагрузку (тротлинг), чтобы защититься от DDoS‑атак и перегрузок (возвращайте код 429 Too Many Requests при превышении лимита).
16. Используйте балансировщик нагрузки — он распределяет запросы между серверами и повышает отказоустойчивость (например, стратегия Round Robin).
17. Разрабатывайте многоуровневые тесты (юнит‑тесты, интеграционные, сквозные) и интегрируйте их в CI/CD‑пайплайн.
18. Настраивайте мониторинг и оповещения (например, через Prometheus, Zabbix), чтобы отслеживать ключевые показатели: скорость отклика, количество запросов, процент ошибок, загрузку серверов.

**Безопасность:**

19. Переходите с HTTP на HTTPS — шифруйте данные для защиты от перехвата и подмены.
20. Продумывайте безопасность на этапе проектирования API, а не после реализации — интегрируйте надёжные механизмы аутентификации, авторизации, шифрования данных, используйте актуальные библиотеки и фреймворки, соблюдайте лучшие практики хранения конфиденциальной информации. Дополнительно:
    - не передавайте конфиденциальные данные в URL‑параметрах — используйте тело запроса или безопасные заголовки (например, Authorization);
    - маскируйте чувствительные данные в логах;
    - возвращайте пользователям обобщённые сообщения об ошибках без внутренней информации;
    - реализуйте механизмы аутентификации (подтверждение личности) и авторизации (определение уровня доступа).
