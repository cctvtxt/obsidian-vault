Центральный процессор — основной вычислительный элемент компьютера, который выполняет инструкции программ. Он обрабатывает данные, выполняет арифметические и логические операции, а также управляет всеми процессами в системе

У процессора есть ядра, на которых выполняются потоки. Ядер может быть, например, 8 (зависит от процессора), но главное запомнить одно ядро = один поток (один водитель машины не может управлять сразу несколькими машинами)

Получается процесс исполняет сами программы. Чем больше ядер на процессоре, тем больше одновременно программ он сможет выполнять




**CPU отвечает за последовательную обработку инструкций, ветвления и быстрое переключение контекста.** В отличие от GPU, процессор считает сложные операции по одной, но делает это с минимальной задержкой. Ядра и тактовая частота — главные характеристики: чем выше частота, тем быстрее исполняется однопоточный код, чем больше ядер — тем больше параллельных задач укладывается без переключений.

Производительность CPU упирается в конкретный сценарий. **Node.js** — однопоточный event loop на каждое ядро, поэтому частотный буст важнее количества ядер: четыре быстрых ядра для четырёх воркеров дадут больше, чем шестнадцать медленных. **Базы данных** (PostgreSQL, MySQL) используют каждое ядро для обработки отдельных транзакций или воркеров — тут количество ядер выходит на первый план при интенсивной параллельной нагрузке. **Интерпретаторы и компиляторы** (Python, Ruby, сборка TypeScript) нагружают одно-два ядра, так что однопоточная производительность снова критична.

Архитектура набора команд делит процессоры на две большие группы. **x86-64** с высокими частотами и мощными одиночными ядрами — стандарт для серверов и десктопов, то что поднимает любой код и любое приложение. **ARM** с эффективностью на ватт и масштабированием до сотен ядер доминирует в мобильных устройствах и облачных гравитационных зонах (AWS Graviton, Apple M-серия), где каждое ядро слабее x86, но суммарная производительность на корзину серверов выше.

Ложка дёгтя — **троттлинг при перегреве** и ограничения памяти. Если процессор перегревается, он сбрасывает частоту: серверная стойка с плохой вентиляцией теряет до тридцати процентов производительности на реальной нагрузке независимо от мощности. Кэш L1, L2, L3 смягчает разницу скорости между CPU и RAM, но если рабочий набор данных превышает L3 кэш производительность падает до скорости памяти — особенно критично для хеш-таблиц и графовых структур данных.

# Чеклист для деплоя

**Какой тип CPU даёт провайдер?** — дешёвые VPS часто используют устаревшие Xeon с низкой однопоточной производительностью или shared CPU, где сосед по гипервизору отжимает такты. Выделенные ядра (dedicated vCPU) гарантируют стабильную частоту, shared (burstable) — дешевле, но latency скачет. Для Node.js, веб-серверов и API нужны dedicated ядра с высокой частотой, для фоновых воркеров и очередей подойдут shared.

**Requests и limits в Kubernetes.** CPU request гарантирует минимальное число ядер, limit — потолок, выше которого под не поднимается. Разница между request и limit создаёт CPU throttling: если limit равен request, под получает ровно столько, сколько запросил. Если limit выше, под может брать свободные такты, но при конкуренции его принудительно троттлят — latency на каждом запросе растёт. Практическое правило: для latency-чувствительных сервисов (API, базы данных) request и limit выставляются одинаково, для фоновых задач limit в два-три раза выше request.

**CPU pinning и NUMA.** Для баз данных и high-load сервисов имеет смысл привязывать поды к конкретным ядрам через CPU manager policy static, чтобы исключить переключение контекста на одном ядре между разными подами. На NUMA-нодах (два сокета на материнской плате) pod может получить ядра из разных NUMA-узлов, что увеличивает задержку доступа к памяти — topology manager в Kubernetes решает это размещением всех ресурсов пода в одном NUMA-узле.
