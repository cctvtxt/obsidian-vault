**GPU справляется только с тем, что можно разбить на тысячи одинаковых подзадач.** Внутри ускорителя находятся тысячи простых ядер: каждое ядро выполняет одну и ту же инструкцию над своим кусочком данных. CPU в таких задачах проигрывает в десятки и сотни раз, потому что он проектировался для быстрого переключения между разными задачами, а не для перемалывания однотипных операций в промышленных масштабах.

Разные задачи ускоряются GPU по-разному. **AI и machine learning** — безусловный лидер: матричные умножения, свёртки, трансформеры идеально параллелятся, а тензорные ядра в NVIDIA делают операции с пониженной точностью в десятки раз быстрее обычных инструкций. **Шейдерная графика и рендеринг** — исторический дом GPU, где каждый фрагмент изображения или вершина модели обрабатывается независимо. **Криптография и криптовалюты** — хеширование SHA-256 и доказательства работы считаются параллельно с максимальной утилизацией. Дженерик-задачи типа сортировки, map-фильтр-reduce или brute-force-поиска тоже ускоряются, но прирост меньше — много времени уходит на передачу данных между CPU и GPU через шину PCI Express.

Главное ограничение GPU — **узкая шина обмена с остальной системой**. Данные копируются из RAM на видеопамять, GPU считает, результат копируется обратно. Эта задержка убивает производительность на маленьких задачах: запуск шейдера на один треугольник или вызов kernel для маленькой матрицы будут медленнее, чем вычисление на CPU. GPU выгодно использовать только на крупных фрагментах данных — от тысяч элементов и выше, иначе оверхед на передачу перевешивает ускорение счёта.

Выбор GPU упирается в тип нагрузки. **NVIDIA CUDA** — стандарт для AI: TensorRT, PyTorch, CUDA-библиотеки заточены именно под неё. **AMD ROCm** — альтернатива, совместимая с большинством AI-фреймворков, но на порядок хуже поддерживается библиотеками. Встроенная графика в CPU (Intel UHD, AMD Radeon) хватает для декодирования видео и интерфейса ОС, но не для CUDA-вычислений — с такими GPU запустить AI-модель не получится.

# Чеклист для деплоя

**GPU в Kubernetes требует отдельного компонента — device plugin.** NVIDIA предоставляет официальный плагин, который регистрирует GPU на каждой ноде и позволяет запрашивать их через `nvidia.com/gpu` в ресурсах пода. Без device plugin контейнер видит CPU и RAM, но не видит GPU. Один GPU можно шарить между несколькими подами через MIG (Multi-Instance GPU) на A100/H100 или Time-Slicing на картах попроще — каждая поделит VRAM и вычислительные блоки.

**VRAM — главный ресурс, заканчивающийся первым.** Модель AI требует определённого объёма видеопамяти под веса и промежуточные активации: Llama 3 8B в FP16 занимает около 16 гигабайт, Stable Diffusion — 6–8 гигабайт. Если VRAM не хватает, вычисления падают в RAM или на CPU — производительность деградирует катастрофически. Размер VRAM надо брать с запасом 20–30 процентов под батчи и временные буферы.

**NodeSelector и taints.** GPU-ноды дорогие, их нужно изолировать от обычных подов. На ноду с GPU ставится taint, на под с AI-нагрузкой — toleration и nodeSelector для привязки к GPU-ноде. Без этого kube-scheduler может запустить на GPU-ноде веб-сервер, который просто займёт ресурсы CPU и RAM, не используя GPU. Для маленьких моделей на одном GPU хватит инстанса VPS с A5000, для тренировок больших моделей нужны кластеры с A100/H100 и NVLink-связкой между картами.
