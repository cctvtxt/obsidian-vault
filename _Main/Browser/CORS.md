Cross-Origin Resource Sharing (CORS) — механизм, использующий дополнительные HTTP-заголовки, чтобы дать возможность агенту пользователя получать разрешения на доступ к выбранным ресурсам с сервера на источнике (домене), отличном от того, что сайт использует в данный момент. Говорят, что агент пользователя делает запрос с другого источника (cross-origin HTTP request), если источник текущего документа отличается от запрашиваемого ресурса доменом, протоколом или портом.


Отличный вопрос — здесь у многих разработчиков есть фундаментальное заблуждение. Давайте разберём по порядку  
CORS ≠ безопасность API. Это защита браузера от одного сайта, делающего запросы от имени пользователя на другой сайт. Сервер обязан защищать себя сам  
Главный принцип  
CORS — это соглашение браузеров, не протокол безопасности. Браузер добровольно отказывается отправлять запрос, если сервер не разрешил источник. `curl` никаким соглашениям не следует: он просто отправляет HTTP-запрос и получает ответ.  
О чём должен заботиться бэкенд-разработчик  
**Аутентификация** — самое важное. Каждый защищённый эндпоинт обязан требовать доказательство личности: JWT-токен, сессионную куку, API-ключ. Без неё любой, кто знает URL, получит данные. `curl -H "Authorization: Bearer <token>"` работает точно так же, как браузер — значит, токен должен быть трудно угадываемым и иметь срок жизни.  
**Авторизация** — аутентификации недостаточно. Пользователь `user_id=42` не должен получать данные `user_id=43`. Это называется IDOR (Insecure Direct Object Reference), и `curl /api/orders/12345` легко эксплуатирует её напрямую. Каждый запрос нужно проверять: «имеет ли этот конкретный пользователь право на этот конкретный ресурс?»  
**Rate limiting** — без него атакующий запускает тысячи запросов в секунду: перебирает пароли, скрейпит базу, нагружает сервер. Нужно ограничивать количество запросов по IP и по токену (например, 100 req/min на пользователя, 10 попыток входа в час).  
**Валидация входных данных на сервере** — никогда не доверяйте тому, что пришло в теле запроса. Атакующий через `curl` может передать любые значения: `{"role": "admin"}`, `-1` в количестве товаров, SQL-инъекцию в поле поиска. Браузерная валидация (форма) легко обходится.  
**HTTPS везде** — если API работает по HTTP, атакующий на одной сети видит все токены и данные в открытом виде.  
**Не раскрывайте лишнего в ответах** — частая ошибка: эндпоинт `/api/user/profile` возвращает весь объект из БД, включая хэш пароля, внутренние флаги, приватные поля. Возвращайте только то, что нужно клиенту.  
**Логирование и мониторинг** — аномальные паттерны (один IP делает 10 000 запросов к `/api/users/{id}` перебирая ID подряд) нужно обнаруживать и блокировать.  
Коротко: зона ответственности  
Что защищает CORS Сервер  
Кража куки соседним сайтом через браузер ✅ —  
curl / скрипт без токена ❌ ✅ аутентификация  
Перебор паролей ❌ ✅ rate limiting  
IDOR (чужие данные по ID) ❌ ✅ авторизация  
SQL-инъекция ❌ ✅ валидация  
Scraping API ❌ ✅ rate limiting + auth  
Правильная установка CORS нужна, но это последняя линия защиты для браузерных сценариев — не замена настоящей серверной безопасности.
