# Автоматизация процессов разработки с ИИ

Ускорение разработки, но потенциальное повышение объема кода, усложнение ревью, усиление всех негативных проявлений классического цикла, галлюцинации, промпт-дрейф, агент угадывает намерения, нарушает замыслы

# Добавление слоя спецификации изменений

- Сохранение контекста изменений - онбординг людей и агентов
- Добавление слоя статической памяти для ИИ
- Экономия на токенах за счет наличия в проекте актуальной спецификации
- Предсказуемая работа AI за счет установленных границ и задач
- Возможность выполнения ревью до реализации на этапе принятия решений

**Документация** — это текстовые материалы, которые описывают компоненты системы, её поведение, API, архитектуру, процессы и правила использования
**Спецификация** — это документ, который детально описывает требования, характеристики и параметры разрабатываемой системы. Спецификация в таком подходе — не отдельный документ для потребителей, а **версионируемый артефакт разработки**, хранящийся рядом с кодом

1.  **Intent (Намерение)** — это бизнес-контекст на человеческом языке
2.  **Contract (Контракт)** — это формальное описание интерфейса
3.  **Behavior (Поведение)** — это сценарии работы
4.  **Constraints (Ограничения)** — это производительность, зависимости, лимиты

# Spec Driven Design

<!-- <style scoped> section { font-size: 28px; } </style> -->

**SDD (Spec-Driven Development)** — подход к разработке, при котором функциональные требования к системе формулируются в виде спецификаций в репозитории рядом с кодом до реализации. Команда определяет контракты всегда до реализации, код пишется по уже утверждённому плану изменений

SDD не заменяет TDD/BDD/DDD и другие, а добавляет дополнительный слой планирования и контрактов между задачами и кодом

Спецификация становится общим контрактом для продукта, разработчиков и AI-агентов, который минимизирует дрейф между задуманным и реализованным

`https://github.com/Engineering4AI/awesome-spec-driven-development`

# Ключевые преимущества OpenSpec

<style scoped> section { font-size: 28px; } </style>

- Подходит для внедрения в разрабатываемые проекты
- Интегрируется с другими тулзами для работы с ИИ
- Реализует разделение состояний спецификаций, версионирование через дельты

```
openspec/
├── project.md
├── config.yaml
├── specs/
│   └── auth/spec.md
└── changes/
    ├── add-two-factor-auth/
    │   ├── proposal.md
    │   ├── design.md
    │   ├── tasks.md
    │   └── specs/auth/spec.md
    └── archive/
```

# Внедрение OpenSpec в проекты

- **Greenfield-проекты** (зелёное поле) — проект с нуля, пустой репозиторий
- **Brownfield-проекты** (заброшенное поле) — существующий проект с кодом, багами, техдолгом, используемым функционалом
  - **_Покрытие спеками готовой логики нецелесообразно_**, это лишняя бюрократия, важный эффект спек ловить расхождения до реализации
  - С каждым заархивированным change спеки органически охватывают большую часть логики — но только там, где реально были изменения: **_покрытие растёт инкрементально_**, вслед за работой
  - До основной работы важно описать исключительно доменные правила в `project.md` и требования к работе ИИ в `settings.yaml`

# Шаг 1. Установка и инициализация OpenSpec

`npm install -g @fission-ai/openspec@latest`

`openspec init`

Эта команда установит скиллы и создаст рабочую директорию:

```text
openspec/
├── specs/       # Актуальное состояние системы
└── changes/     # Предлагаемые изменения
```

# Шаг 2. Создание `project.md`

В актуальных версиях `OpenSpec` файл не генерируется автоматически при вызове `openspec init`, целесообразно создать его для дополнительного утверждения доменных правил

Он утверждает доменные правила (стек, структура, конвенции) до первой работы
и подаётся агентам как контекст при каждом планировании.

Он может включать в себя разделы: Purpose, Tech Stack, Folder Structure, API Conventions, Error Handling, Security, Performance, Code Style, Domain Context, AI Context Rules, Known Issues, Development.

# Настройка. Интеграция с OpenCode

После вызова `openspec init` будут установлены необходимые скиллы и команды для `opencode` через которые строится работа по SDD: `/opsx-propose`, `/opsx-apply`, `/opsx-update`, `/opsx-sync`, `/opsx-archive`, `/opsx-explore`

Для работы `OpenCode` только по SDD целесообразно в корне проекта прописать правила в `.opencode/instructions.md` или в `AGENTS.md`:

```markdown
1. Запрещено писать продуктовый код, пока нет согласованного изменения в `openspec/changes/<change-id>/`.
2. Код должен строго реализовывать требования из `specs/` внутри активного change.
3. Код считается завершенным только тогда, когда каждый `Scenario` покрыт автотестом.
4. Выполняй задачи строго по очереди из `tasks.md`, отмечая прогресс чекбоксами `[x]`.
5. Не выходи за рамки Scope, определенного в `proposal.md`.
```

# Настройка. Добавление этапа проверки спек

```yaml
on: [push, pull_request]

jobs:
  validate-specs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: "20"
      - name: Install OpenSpec CLI
        run: npm install -g @openspec/cli
      - name: Validate OpenSpec Integrity
        run: openspec validate --strict
```

# Шаг 3. `/opsx-propose` — Создание изменения

В консоли создайте ветку под задачу:

```bash
git checkout -b feat/user-block-spam
```

В OpenCode:

```
/opsx-propose Блокировать пользователя на 24 часа, если он отправляет более 50 сообщений в минуту
```

ИИ создаёт `openspec/changes/user-block-spam/` и генерирует **весь комплект артефактов разом**, задавая пользователю уточняющие вопросы по реализации

Также для ведения дискуссий по проекту можно вызывать `/opsx-explore`

---

### Артефакт `/changes/<feature>/proposal.md`

```markdown
# Spam protection

## Problem

Пользователи-спамеры отправляют поток сообщений, что мешает остальным участникам и создаёт избыточную нагрузку на сервер.

## Proposed change

Блокировать пользователя на 24 часа, если он отправляет более 50 сообщений в минуту.

## Scope

- Подсчёт количества сообщений пользователя в минуту
- Автоматическая блокировка при превышении лимита 50 сообщений/мин
- Снятие блокировки автоматически через 24 часа
- Исключение администраторов из-под блокировки

## Out of scope

- Ограничение приватных сообщений
- Ручная блокировка и разблокировка модераторами

## Impact

- Сервис сообщений
- Модель пользователя (поле blocked_until)
```

### Артефакт `/changes/<feature>/specs/<capability>/spec.md`

```markdown
## ADDED Requirements

### Requirement: Ограничение частоты сообщений

Система ОБЯЗАНА блокировать пользователя на 24 часа, если он отправляет более

```

# Шаг 4. `/opsx-update` Ревизия артефактов

В OpenCode:

```
/opsx-update уточни, что блокировка снимается автоматически через 24 часа
```

ИИ перечитывает уже сгенерированные `proposal.md`, `spec.md`, `design.md`, `tasks.md` и правит их по замечаниям пользователя, сохраняя согласованность

При неоднозначном решении ИИ задаёт вопросы в чате и предлагает варианты:

```markdown
> Как хранить счётчик сообщений за минуту?
>
> - А. Redis (sliding window) — честный лимит, без скачков на границе минуты;
> - Б. Счётчик in-memory в процессе — просто, но сбрасывается при рестарте;
> - В. Fixed window в БД — без новых зависимостей, но нагрузка на БД при росте.
```

# Шаг 5. `/opsx-apply` Реализация изменения

В OpenCode:

```
/opsx-apply
```

ИИ выбирает change, читает открытые задачи, последовательно выполняет, пишет и выполняет тесты, если тесты падают, чинит код.

Последовательно проставляет для каждой выполненной задачи `- [x]`.

В конце возвращает отчёт: сколько задач сделано, что осталось.

# Шаг 6. `/opsx-sync` и `/opsx-archive` Завершение

В OpenCode — сначала сливаем дельта-спеки в основную спецификацию:

```
/opsx-sync
```

ИИ забирает изменения спец из `openspec/changes/user-block-spam/specs/`.

Затем архивируем изменение:

```
/opsx-archive
```

ИИ переносит папку изменения в `openspec/changes/archive/`, папка переименовывается в `openspec/changes/archive/YYYY-MM-DD-user-block-spam/`.
