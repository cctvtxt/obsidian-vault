

`to-spec` по своей документации превращает текущий разговор в одну спецификацию и публикует её в issue tracker; его шаблон строится вокруг Problem Statement, Solution и большого списка User Stories

**PRD** — это _Product Requirements Document_, то есть **документ требований к продукту**.

Он описывает:

- **что** нужно построить;
- **для кого** это делается;
- **какую проблему** решает функция или продукт;
- какие возможности должны быть реализованы;
- как проверить, что результат удовлетворяет требованиям.

PRD помогает команде договориться о границах задачи и служит общей точкой отсчёта для product manager, разработчиков, дизайнеров и QA

**PRD — это описание продукта и его требований на уровне целей, пользователей и функциональности; OpenSpec — более формальный инженерный формат для реализации и проверки поведения**.

`/to-spec` хорошо использовать как генератор подробной PRD/spec из разговора, но для OpenSpec нужен дополнительный этап преобразования. Если хочется полной совместимости, лучше добавить собственную инструкцию или wrapper-skill, который после `/to-spec` автоматически раскладывает результат в OpenSpec-структуру и запускает валидацию.
______
SDD в OpenSpec можно усилить сохранением PRD и ADR. Но в стандартной схеме OpenSpec они **не являются отдельными встроенными артефактами**

| Артефакт      | Главный вопрос                                               | Срок жизни                      |
| ------------- | ------------------------------------------------------------ | ------------------------------- |
| PRD           | Зачем нужен продукт или функция? Для кого она предназначена? | Пока актуальна продуктовая цель |
| `proposal.md` | Что именно меняется в этом change?                           | Жизненный цикл change           |
| `spec.md`     | Какое поведение системы является контрактом?                 | Постоянно                       |
| `design.md`   | Как технически реализовать изменение?                        | Жизненный цикл change           |
| ADR           | Почему выбрано именно такое архитектурное решение?           | Постоянно                       |
| `tasks.md`    | Какие шаги нужно выполнить?                                  | До завершения реализации        |

PRD       → продуктовая потребность
OpenSpec  → наблюдаемое поведение
ADR       → долгосрочное архитектурное решение
Tasks     → конкретная работа разработчика

В `proposal.md` можно ссылаться на PRD + Вариант с custom schema

PRD и ADR — обычные version-controlled документы OpenSpec — behavioral contract и change workflow

**Итог:** стандартный OpenSpec сохраняет `proposal`, `design` и `tasks` внутри архива change, но не ведёт отдельные PRD и ADR как долгосрочные first-class документы. Для этого нужно либо хранить их самостоятельно в `docs/`, либо подключить custom schema вроде `spec-driven-with-adr` и расширить workflow PRD-артефактом

________

можно использовать `/grill-me` вместе с `/opsx:propose`, но **автоматического соединения между ними по умолчанию нет**. Надёжнее запускать их последовательно в одном диалоге, а не рассчитывать, что `opsx-propose` сам вызовет другой skill

`/grill-me` является самостоятельным stateless skill: он не создаёт файлов и оставляет результат только в контексте разговора. Его нужно запускать явно — агент сам обычно не вызывает его

При этом `grill-me` не гарантирует «100% покрытия». Он зависит от качества ответов, модели и размера задачи. Кроме того, он сам по себе не исследует кодовую базу: если вопрос можно решить только чтением репозитория, лучше использовать `/opsx:explore` или `grill-with-docs`. Последний вариант умеет сопоставлять обсуждение с кодом и сохранять результаты в `CONTEXT.md` и ADR

По документации `/opsx:update` не создаёт отсутствующие артефакты — для этого используется `/opsx:continue`. Также если обсуждение изменило саму цель задачи, а не только способ реализации, лучше создать новый change вместо обновления старого
