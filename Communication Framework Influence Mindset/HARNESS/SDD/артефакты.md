Ниже — тот же перечень, но каждый артефакт описан отдельным абзацем. Под `Definition of Dan` я понимаю `Definition of Done`.

## Основные артефакты

`prd/<feature>.md` — PRD описывает, зачем нужна функция, какую пользовательскую или бизнес-проблему она решает, кто её будет использовать и как измерить успех. PRD является продуктовым источником контекста, а не техническим планом: он помогает OpenSpec не потерять исходную цель при декомпозиции задачи.

`adr/<number>-<decision>.md` — ADR фиксирует архитектурное решение, его контекст, рассмотренные альтернативы, выбранный вариант и последствия. В отличие от `design.md`, который обычно относится к текущему change, ADR сохраняет долгоживущую причину решения после завершения конкретной задачи. Классическая структура ADR включает title, status, context, decision и consequences.[[adr.github](https://adr.github.io/)]

`openspec/specs/<capability>/spec.md` — это нормативное описание наблюдаемого поведения системы. В нём должны находиться requirements и scenarios, по которым можно проверить реализацию. OpenSpec рассматривает specs как source of truth текущего поведения, тогда как PRD объясняет продуктовую мотивацию, а ADR — архитектурную причину.[[openspec](https://openspec.dev/docs/opsx)]

`openspec/changes/<change>/proposal.md` — proposal описывает намерение конкретного изменения: зачем оно требуется, что входит в scope и какие части системы затрагиваются. Это временный change-level документ, который связывает PRD с изменяемыми OpenSpec requirements.

`openspec/changes/<change>/design.md` — design объясняет, как именно будет реализован change: какие модули изменятся, какие данные появятся, как будут взаимодействовать сервисы и какие технические ограничения существуют. Он не должен становиться постоянной энциклопедией архитектуры; долгоживущие решения лучше переносить в ADR.

`openspec/changes/<change>/tasks.md` — tasks превращают согласованный дизайн и requirements в последовательность действий. Этот файл отвечает на вопрос «что нужно сделать», но не заменяет DoD: выполненные задачи ещё не означают, что изменение прошло тесты, review, migration и production verification.

## Процесс и готовность

`docs/process/definition-of-ready.md` — Definition of Ready определяет, когда задачу можно передавать в OpenSpec или начинать реализацию. В неё можно включить наличие ясной проблемы, scope, затрагиваемых сервисов, testable requirements, API-контрактов, migration strategy, security impact и отсутствие блокирующих вопросов. DoR защищает команду от начала работы над недостаточно сформулированной задачей. Типовые признаки ready-задачи — ясность, реализуемость и тестируемость.[[handbook.gitlab](https://handbook.gitlab.com/handbook/customer-success/professional-services-engineering/professional-services-delivery-methodology/definition-of-ready/)]

`docs/process/definition-of-done.md` — Definition of Done описывает критерии полного завершения работы. Для backend change туда обычно входят реализованные requirements, пройденные unit и integration tests, contract compatibility, обновлённая observability, завершённый code review, проверенные migration и rollback, а также актуальные runbooks. DoD превращает «код написан» в проверяемое определение production-ready результата.

`docs/process/quality-gates.md` — quality gates фиксируют контрольные точки процесса: что проверяется перед proposal, перед implementation, перед merge и перед release. Такой документ помогает автоматизировать часть DoR и DoD через CI, OpenSpec validation, contract checks, security scans и обязательные reviews.

`docs/process/working-agreement.md` — working agreement описывает командные правила использования OpenSpec, PRD и ADR. В нём можно зафиксировать, когда создавать новый change, кто утверждает ADR, когда нужен внешний issue, кто обновляет spec и что делать при изменении scope. Он предотвращает разные интерпретации процесса членами команды.

`docs/process/adr-ready.md` — ADR Ready определяет, когда архитектурное решение достаточно проработано для фиксации. Документ может требовать архитектурной значимости проблемы, описанного контекста, сравнения альтернатив, указанных trade-offs, понятных последствий и назначенного reviewer. Это предотвращает создание ADR ради каждого незначительного выбора библиотеки.

`docs/process/review-policy.md` — review policy описывает обязательные виды проверки для разных типов изменений. Например, изменение protobuf требует contract review, изменение authentication — security review, изменение схемы БД — database review, а изменение SLO — operations review. Такой файл связывает тип change с нужными экспертами.

## Архитектура и домен

`docs/architecture/system-context.md` — system context показывает систему снаружи: пользователей, внешние сервисы, интеграции, основные потоки и trust boundaries. Он помогает агенту и разработчику понять окружение проекта до чтения отдельных сервисов и определить, какие внешние зависимости могут быть затронуты изменением.

`docs/architecture/container.md` — container diagram описывает крупные исполняемые части системы: API Gateway, микросервисы, базы данных, брокеры и внешние провайдеры. Это полезный уровень детализации между бизнес-контекстом и исходным кодом; его можно использовать для определения границ OpenSpec change. Для такой документации подходит C4-модель с уровнями context, container, component и code.[[c4model](https://c4model.com/diagrams)]

`docs/architecture/service-catalog.md` — service catalog содержит краткое описание каждого микросервиса: его ответственность, владельца, протоколы, хранилище, события, зависимости и SLO. Он ускоряет onboarding и помогает быстро определить owner и blast radius изменения.

`docs/architecture/dependency-map.md` — dependency map показывает направленные зависимости между сервисами, базами данных, брокерами и внешними системами. В отличие от service catalog, который описывает сервисы по отдельности, dependency map позволяет увидеть, какие компоненты будут затронуты при изменении конкретного API, события или хранилища.

`docs/architecture/data-flow.md` — data-flow document описывает, как данные проходят через систему от клиента до хранилища, брокера и downstream-сервисов. Он особенно важен для PII, authentication claims, платежей, audit events и распределённых транзакций, где ошибка в маршруте данных может привести к security или consistency-проблемам.

`docs/architecture/deployment.md` — deployment document связывает логические компоненты с runtime-инфраструктурой: Kubernetes workloads, namespaces, databases, queues, regions, ingress и secrets. Он помогает OpenSpec учитывать не только изменение кода, но и последствия для deployment topology.

`docs/architecture/capacity-model.md` — capacity model фиксирует ожидаемые объёмы запросов, throughput, storage growth, количество consumers и пределы масштабирования. Такой документ помогает не забыть performance и capacity requirements при создании спецификации.

`docs/domain/glossary.md` — glossary задаёт точные значения терминов предметной области. Он предотвращает ситуации, когда `user`, `account`, `identity`, `tenant` или `session` используются в разных спецификациях с разными смыслами.

`docs/domain/domain-model.md` — domain model описывает сущности, связи, aggregate boundaries и основные состояния домена. Это более стабильный документ, чем отдельный PRD: он объясняет текущую модель системы, на которую должны опираться новые requirements.

`docs/domain/invariants.md` — invariants фиксируют правила, которые всегда должны оставаться истинными. Например, заказ не может быть оплачен дважды, отозванный refresh token нельзя повторно использовать, а event ID должен быть уникальным. Invariants полезны как источник scenarios, property-based tests и transaction constraints.

`docs/domain/context-map.md` — context map показывает bounded contexts и отношения между ними. Он помогает не смешивать термины разных доменов и не создавать лишние прямые зависимости между микросервисами.

`docs/domain/state-machines.md` — state machine описывает разрешённые состояния и переходы сущности. Такой документ полезен для orders, payments, sessions, subscriptions и workflows, где обычного списка полей недостаточно для понимания допустимого поведения.

## Контракты и данные

`docs/contracts/openapi/<service>.yaml` — OpenAPI описывает HTTP-контракт: paths, methods, request и response schemas, status codes, headers, authentication и errors. OpenSpec может описать поведение endpoint, но OpenAPI должен фиксировать точную форму публичного API и может валидироваться в CI.

`docs/contracts/proto/<service>/v1/*.proto` — protobuf-файлы являются контрактом gRPC-взаимодействия. Они фиксируют services, RPC methods, messages, field numbers и package versions. Для OpenSpec это отдельный machine-readable слой, из которого можно генерировать клиентов, серверные интерфейсы и contract tests.

`docs/contracts/asyncapi/<domain>.yaml` — AsyncAPI или аналогичный документ описывает события и сообщения: topic, subject, payload, producer, consumers, delivery semantics и schema version. Он особенно полезен для Kafka и NATS, где изменение сообщения может сломать несколько независимых consumers.

`docs/contracts/event-catalog.md` — event catalog даёт человекочитаемый список событий и их владельцев. Для каждого события можно указать producer, consumers, ordering key, delivery guarantee, replay policy, retention и наличие PII. Он быстрее для навигации, чем поиск по всем AsyncAPI или protobuf-файлам.

`docs/contracts/compatibility.md` — compatibility policy описывает, какие изменения считаются backward-compatible для HTTP, gRPC и событий. В ней можно зафиксировать правила добавления и удаления полей, период поддержки старых версий, порядок миграции consumers и требования к schema evolution.

`docs/data/data-dictionary.md` — data dictionary описывает смысл важных полей, их типы, владельцев, изменяемость, чувствительность и source of truth. Он помогает устранить неоднозначность между `id`, `externalId`, `tenantId`, `status`, `createdAt`, `deletedAt` и похожими полями.

`docs/data/data-classification.md` — data classification разделяет данные на public, internal, confidential, sensitive или PII. Для каждого класса можно определить правила хранения, логирования, шифрования, retention и передачи между сервисами.

`docs/data/migration-plan.md` — migration plan описывает последовательность безопасного изменения данных или схемы БД. Обычно он включает expand-and-contract этапы, backfill, dual write, переключение чтения, удаление старого поля и rollback limitations.

`docs/data/retention-policy.md` — retention policy фиксирует, как долго хранятся пользователи, сессии, audit events, сообщения, логи и backups. Это помогает связать database design, security requirements, compliance и operational cleanup jobs.

## Security и эксплуатация

`docs/security/threat-model.md` — threat model описывает actors, assets, entry points, trust boundaries, угрозы и меры защиты. Он добавляет к PRD и OpenSpec перспективу злоумышленника: не только что должна делать система, но и как её могут атаковать. OWASP рассматривает threat modeling как отдельный процесс анализа архитектуры, угроз и mitigations.[[owasp](https://owasp.org/www-project-threat-modeling/)][[devguide.owasp](https://devguide.owasp.org/en/04-design/01-threat-modeling/07-practical-threat-modeling/)]

`docs/security/authentication-model.md` — authentication model фиксирует различия между user, identity, account, session, access token и refresh token. В нём можно описать logout, revocation, token rotation, key rotation, mTLS, service accounts, scopes, roles и claims.

`docs/security/authorization-model.md` — authorization model описывает, кто и к каким ресурсам имеет доступ. Он может содержать RBAC/ABAC-политику, ownership rules, tenant isolation, administrative permissions и service-to-service authorization.

`docs/security/security-controls.md` — security controls превращают общие требования безопасности в проверяемый baseline. Например, secrets не должны попадать в Git или логи, refresh tokens нельзя логировать, signing keys нужно ротировать, а административные действия должны создавать audit events.

`docs/security/secrets-and-keys.md` — документ описывает жизненный цикл секретов и ключей: генерацию, хранение, выдачу, rotation, revocation, backup и incident response. Он особенно полезен для JWT signing keys, mTLS certificates, database credentials и cloud workload identity.

`docs/security/abuse-cases.md` — abuse cases описывают нежелательное использование системы: replay token, brute force, privilege escalation, enumeration, message flooding и повторную доставку команды. Эти сценарии можно связывать с security tests и OpenSpec negative scenarios.

`docs/operations/runbooks/<incident>.md` — runbook описывает пошаговые действия при конкретной аварии: симптомы, команды диагностики, безопасные mitigation actions, escalation path, rollback и критерий восстановления. Runbook отвечает на вопрос «что делать оператору сейчас», которого обычно нет в PRD или spec.

`docs/operations/slo.md` — SLO document фиксирует availability, latency, throughput, error rate и error budget для критических сервисов. Он связывает non-functional requirements из OpenSpec с dashboards, alerts и release policy.

`docs/operations/observability.md` — observability guide описывает обязательные metrics, logs, traces, correlation IDs, dashboards, alerts, redaction и cardinality rules. Благодаря ему изменение считается незавершённым, если оно добавляет новую critical path, но не добавляет способ её наблюдать.

`docs/operations/incident-response.md` — incident response описывает процесс работы во время аварии: обнаружение, назначение incident commander, severity, коммуникацию, mitigation, восстановление и follow-up actions. Это процессный слой эксплуатации; SRE рассматривает incident response как самостоятельную инженерную практику.[[sre](https://sre.google/workbook/index/)]

`docs/operations/postmortems/<incident>.md` — postmortem сохраняет impact, timeline, root cause, contributing factors и corrective actions после инцидента. Его ценность в превращении производственного опыта в новые ADR, requirements, alerts, tests и runbooks.

`docs/operations/disaster-recovery.md` — disaster recovery document описывает восстановление после потери региона, базы данных, брокера или критического storage. В нём фиксируются RPO, RTO, backup policy, restore procedure, failover и ограничения восстановления.

`docs/operations/business-continuity.md` — business continuity описывает, как продолжать критические бизнес-процессы при недоступности отдельных компонентов. Это шире технического disaster recovery: документ может включать manual fallback, degraded mode, communication plan и приоритеты восстановления.

`docs/operations/on-call.md` — on-call guide описывает rotation, ownership, escalation, paging channels и правила передачи дежурства. Он связывает технические alerts с конкретными людьми и командами.

## Тестирование и поставка

`docs/testing/test-strategy.md` — test strategy объясняет, какие виды тестов применяются к разным уровням системы. Например, domain rules проверяются unit tests, взаимодействие с PostgreSQL и брокером — integration tests, границы сервисов — contract tests, а критические пользовательские сценарии — E2E tests.

`docs/testing/test-matrix.md` — test matrix связывает requirements и scenarios с конкретными тестами и их статусом. Она помогает обнаружить сценарий, который описан в `spec.md`, но не имеет автоматической проверки.

`docs/testing/contract-testing.md` — contract testing document фиксирует, как проверяются совместимость producer и consumer. Для gRPC, Kafka и NATS он помогает определить, кто публикует контракт, кто его проверяет и в какой момент CI должен блокировать несовместимое изменение.

`docs/testing/load-testing.md` — load-testing plan описывает профили нагрузки, target throughput, latency objectives, data volume и критерии успешности. Он полезен для изменений, которые влияют на Redis, PostgreSQL, Kafka consumers или API rate limits.

`docs/testing/security-testing.md` — security testing document связывает threat model с конкретными проверками: replay, brute force, authorization bypass, injection, secret leakage и tenant isolation. Он превращает список угроз в воспроизводимые тестовые сценарии.

`docs/traceability-matrix.md` — traceability matrix связывает цепочку `PRD → requirement → scenario → ADR/design → task → commit/PR → test → release`. Она особенно ценна для authentication, billing, compliance и других изменений, где нужно доказать, что каждое требование реализовано и проверено.

`docs/release/release-plan.md` — release plan описывает rollout: feature flags, deployment order, canary, migration phases, monitoring window, release owner и условия остановки. OpenSpec объясняет, что должно измениться, а release plan — как безопасно доставить это изменение.

`docs/release/rollback-plan.md` — rollback plan описывает, как отменить код, конфигурацию или deployment и что делать с уже изменёнными данными и сообщениями. Для distributed systems это особенно важно, потому что код часто можно откатить, а опубликованные события или выполненную миграцию — нет.

`docs/release/compatibility-window.md` — compatibility window определяет, сколько времени старые и новые версии producers и consumers должны работать одновременно. Такой документ нужен для rolling deployment, blue-green deployment, protobuf evolution и event schema migration.

`CHANGELOG.md` — changelog перечисляет заметные изменения между версиями. Он ориентирован на пользователей, операторов и интеграторов, а не на внутреннюю реализацию; его не нужно делать копией `tasks.md`.

`docs/release/release-notes/<version>.md` — release notes объясняют конкретную поставку: новые возможности, breaking changes, migration actions, known issues и operational impact. Они полезнее changelog для крупных релизов или изменений публичного API.

## Репозиторий и команда

`README.md` — README является стартовой точкой репозитория. Он должен объяснять назначение проекта, быстрый запуск, основные команды, структуру каталогов и ссылки на PRD, ADR, OpenSpec, contracts и runbooks.

`CONTRIBUTING.md` — CONTRIBUTING описывает правила работы с репозиторием: branching, commits, pull requests, tests, review, OpenSpec changes, migrations и generated files. Он снижает количество процессных ошибок у новых участников.

`SECURITY.md` — SECURITY определяет supported versions, security contact и порядок безопасного сообщения об уязвимости. Это отдельный public-facing документ, который не должен смешиваться с внутренним threat model.

`CODEOWNERS` — CODEOWNERS связывает каталоги с командами или ответственными разработчиками. Это не обычная документация, но важный ownership artifact: он помогает автоматически назначать reviewers для security, contracts, migrations и архитектурных каталогов.

`AGENTS.md` или `CLAUDE.md` — этот файл содержит правила работы AI-агента с проектом: какие документы читать, какие команды запускать, как обновлять OpenSpec, когда создавать ADR и какие изменения запрещены. Он описывает процесс работы агента, но не должен становиться источником бизнес-поведения вместо `spec.md`.

`docs/agents/skill-usage.md` — skill usage guide объясняет, какой skill использовать для какого типа задачи. Например, `/grill-with-docs` применяется до proposal, `/opsx:update` — после изменения решения, `/tdd` — во время реализации, а `/code-review` — перед merge. Это уменьшает случайное и непоследовательное применение AI-инструментов.

`docs/assumptions.md` — assumptions log содержит допущения, на которых строятся архитектура и план. Примеры: Kafka работает с at-least-once delivery, PostgreSQL является source of truth, Redis может потерять данные, а все сервисы передают correlation ID. Если допущение меняется, это хороший триггер для ADR или нового OpenSpec change.

`docs/open-questions.md` — open questions содержит временный список нерешённых вопросов. Он помогает не потерять неопределённость между discovery и proposal, но после решения вопрос нужно перенести в PRD, ADR, spec или design, а не оставлять в списке навсегда.

`docs/risk-register.md` — risk register содержит риски, вероятность, impact, mitigation, owner и статус. В отличие от threat model, он включает не только security threats, но и migration risk, vendor dependency, capacity risk, delivery risk и operational risk.

`docs/research/<topic>.md` — research note сохраняет результаты исследования, ссылки на источники, эксперименты и ограничения найденного решения. Он полезен, когда design или ADR основаны на внешней документации, поведении библиотеки, протоколе или cloud provider.

`docs/rfcs/<number>-<topic>.md` — RFC используется для широкого обсуждения потенциального изменения до того, как оно стало согласованным ADR или OpenSpec change. RFC хорошо подходит для нескольких альтернатив и комментариев команды; после принятия его выводы обычно переносятся в ADR, PRD или design.

`docs/decisions.md` — decision log представляет собой компактный список решений с датами, владельцами и ссылками на подробные ADR. Он удобен для быстрого поиска, но не должен заменять сами ADR: это индекс, а не полное объяснение решения.

## Какой набор выбрать

Для небольшого репозитория достаточно начать с `README.md`, `AGENTS.md`, `definition-of-ready.md`, `definition-of-done.md`, `glossary.md`, `service-catalog.md`, `contracts/`, `adr/`, `prd/` и `openspec/`.

Для микросервисной backend-системы с PostgreSQL, Redis, Kafka, NATS и gRPC я бы добавил `threat-model.md`, `authentication-model.md`, `compatibility.md`, `migration-plan.md`, `test-strategy.md`, `test-matrix.md`, `slo.md` и несколько operational runbooks.

Полная связь между слоями может выглядеть так:

```
PRD                    → зачем создаём изменение
Definition of Ready    → достаточно ли задача проработана
RFC                    → какие варианты рассматривали
ADR                    → почему выбрали конкретное решение
OpenSpec proposal      → что изменяем сейчас
OpenSpec spec          → какое поведение требуется
OpenSpec design        → как это реализуем
OpenSpec tasks         → какие шаги выполняем
Test matrix            → чем проверяем requirements
Definition of Done     → действительно ли закончили
Release plan           → как доставляем изменение
Runbook                → что делаем при проблеме
Postmortem             → чему научились после инцидента
```

Важно не создавать несколько документов с одинаковой ролью. Например, `design.md`, RFC и ADR могут пересекаться, поэтому стоит заранее определить границы: RFC обсуждает варианты, `design.md` описывает текущий change, а ADR сохраняет принятое долгоживущее решение.
