# Решения для оркестрации контейнеров

## Классификация

### 1. Полноценные Kubernetes-дистрибутивы
- **Vanilla Kubernetes (kubeadm)** — эталонная сборка
- **RKE / RKE2** (Rancher) — production-grade, CIS-hardened
- **OpenShift** (Red Hat) — enterprise K8s «всё включено»
- **Tanzu** (VMware) — enterprise K8s для vSphere
- **GKE / EKS / AKS** — управляемые облачные K8s

### 2. Лёгкие Kubernetes-дистрибутивы
- **K3s** (SUSE/Rancher) — один бинарник, SQLite по умолчанию
- **K0s** (Mirantis) — похож на K3s, но «чистый» upstream K8s
- **MicroK8s** (Canonical/Ubuntu) — snap-пакет, модульный
- **Talos Linux** — immutable OS, K8s как ядро системы
- **k3d / kind / minikube** — локальные dev-кластеры (не для прода)

### 3. Альтернативы Kubernetes
- **Docker Swarm** — встроен в Docker Engine
- **HashiCorp Nomad** — оркестратор не только контейнеров
- **Apache Mesos + Marathon** — «старая гвардия», datacenter-scale
- **Dokku** — PaaS на одном хосте (Heroku-like)
- **Coolify** — self-hosted PaaS (альтернатива Vercel/Heroku)
- **CapRover** — простой PaaS с GUI

### 4. Минимальные / «оркестрация без оркестратора»
- **Docker Compose** — декларативный запуск на одном хосте
- **Podman + Quadlet (systemd)** — rootless-контейнеры как unit-файлы
- **systemd + OCI-контейнеры** — контейнер как сервис
- **Portainer** — GUI-обёртка над Compose/Swarm/K8s

## Рекомендация по размеру команды

```
1 человек, <10 сервисов
  → Docker Compose / Dokku / Coolify

2–3 человека, 10–20 сервисов, 1–2 хоста
  → Docker Compose + Portainer  ИЛИ  Docker Swarm

2–3 человека, 10–30 сервисов, 3+ хоста
  → K3s (если есть K8s-опыт)  ИЛИ  Nomad (если нет)

5+ человек, 30+ сервисов
  → K3s / RKE2 / Managed K8s
```

> **Ключевой вывод для маленькой команды:** каждая технология, которую вы внедряете, — это **налог на ваше время**. K8s (даже K3s) заберёт 20–40% времени одного инженера на поддержку кластера. Если у вас 2 человека — это 20–40% всей команды. Убедитесь, что проблема, которую вы решаете, стоит этой цены.


# Вы абсолютно правы — но есть нюанс

Да, это **главная цель** оркестратора: вы перестаёте вручную перезапускать упавшие сервисы, балансировать нагрузку и думать о том, на каком сервере что запущено. Это не миф, это реальность.

Но фраза **«настроил один раз»** — вот где кроется подвох.

## Что реально происходит после «первоначальной настройки»

### ✅ От чего вы **избавитесь** (навсегда)

| Ручная работа в Compose | В K8s это автоматизировано |
|---|---|
| `ssh server && docker compose restart app` | Liveness probe → рестарт сам |
| Ручное переключение на backup-сервер при падении | K8s переносит поды на живую ноду |
| `docker compose up -d --scale app=3` | HPA масштабирует по CPU/RAM |
| Ручной rolling update с простоями | `kubectl set image` → zero-downtime |
| Проверка «а все ли контейнеры живы?» | Контроллеры следят 24/7 |
| Ручная настройка nginx для нового сервиса | Ingress + cert-manager → авто-TLS |

Это **огромный выигрыш**. Никто не спорит.

---

### ⚠️ Что **появится взамен** (и это не разовая работа)

#### 1. Обновление самого кластера
```
K3s выходит каждые ~2 месяца (minor), патчи — каждые 2–4 недели.
```
- Обновить control-plane
- Обновить worker-ноды по очереди
- Проверить, не сломались ли API-версии манифестов (K8s деприкейтит API регулярно)
- Обновить Helm-чарты зависимостей

**В Compose:** `apt upgrade docker-ce` раз в полгода, если вспомните.

#### 2. Сертификаты
- TLS-сертификаты Ingress (даже с cert-manager — они иногда ломаются)
- Внутренние сертификаты etcd / K3s (ротация через 12 месяцев)
- Сертификаты между нодами

**В Compose:** один certbot + cron, и вы забыли.

#### 3. Storage
- PVC завис, PV не освобождается → разбираться
- Longhorn/Ceph деградировал → восстанавливать реплики
- Диск на ноде забился образами → чистить `crictl rmi --prune`

**В Compose:** `docker system prune` раз в месяц.

#### 4. Сеть и DNS
- CoreDNS не резолвит сервис → почему?
- Pod в `CrashLoopBackOff` из-за NetworkPolicy → дебажить
- CNI-плагин обновился и сломал связь между нодами

**В Compose:** `docker network ls`, всё на одном bridge.

#### 5. Мониторинг самого оркестратора
- etcd (или SQLite) тормозит → кластер деградирует
- kubelet на ноде упал → нода `NotReady`
- Кончились ресурсы → поды в `Pending`, и никто не знает почему

**В Compose:** `htop` + `docker stats`.

#### 6. Инциденты нового типа
| Compose-инцидент | K8s-инцидент |
|---|---|
| «Контейнер упал» | «Под в ImagePullBackOff из-за истёкшего секрета registry» |
| «Место на диске кончилось» | «Eviction threshold: нода начала убивать поды» |
| «Nginx не стартует» | «Ingress controller в CrashLoop из-за невалидного Ingress-ресурса» |

Суть: **проблемы не исчезают — они становятся абстрактнее и сложнее в диагностике**.

## Аналогия

Представьте, что вы пересели с **велосипеда** (Compose) на **автомобиль** (K8s).

| | Велосипед | Автомобиль |
|---|---|---|
| Ехать быстрее? | Нет | **Да ✅** |
| Крутить педали? | Да | **Нет ✅** |
| Бензин? | Не нужен | **Нужен ⚠️** |
| ТО, масло, фильтры? | Нет | **Каждые 10 тыс. ⚠️** |
| Страховка, налоги? | Нет | **Каждый год ⚠️** |
| Сломался в дороге? | Починил на месте | **Эвакуатор ⚠️** |

Автомобиль **объективно лучше** для длинных дистанций. Но если вы ездите 2 км до магазина — велосипед проще.

---

## Когда автоматизация **окупается**

| Ситуация | Окупаемость |
|---|---|
| Сервисы падают ночью, и кто-то встаёт их поднимать | ✅ **Сразу** |
| Деплой занимает часы из-за ручных шагов | ✅ **Быстро** |
| 5+ серверов, и вы путаетесь, где что | ✅ **Быстро** |
| Команда растёт, и новички не могут развернуть среду | ✅ **За 1–2 мес.** |
| Всё работает стабильно, деплой раз в неделю, 2 сервера | ❌ **Не окупится** |
| Единственный «девопс» и так перегружен | ❌ **Станет хуже** |

## Итог

> **Вы правы:** K8s снимает рутину перезапусков и масштабирования. Это не преувеличение.
>
> **Но:** он не снимает рутину *вообще* — он **заменяет один тип рутины на другой**. Простая рутина (перезапусти контейнер) меняется на сложную (разберись, почему PV в состоянии Released, а под в Pending).
>
> **Для маленькой команды** вопрос не «автоматизирует ли K8s работу?», а **«хватит ли у нас экспертизы, чтобы решать *новые* проблемы быстрее, чем мы решали *старые*?»**.

Если да — переходите, не сомневайтесь. Если нет — начните с Compose + Portainer + хороший CI/CD, а K8s отложите до момента, когда боль от Compose станет невыносимой.
