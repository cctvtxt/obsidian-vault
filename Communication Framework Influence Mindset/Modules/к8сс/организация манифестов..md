# Организация манифестов Kubernetes

## Подходы к организации файлов

### Один файл vs множество файлов

В Kubernetes нет жёстких правил о том, как именно разбивать манифесты по файлам. Технически можно описать все ресурсы в одном единственном YAML-файле, разделяя их через `---`. Однако на практике это быстро превращается в нечитаемую простыню. Противоположный подход — один файл на один ресурс — даёт максимальную гранулярность, но может привести к десяткам файлов даже для простого приложения. Золотая середина — группировать логически связанные ресурсы (например, Deployment и его Service в одном файле или рядом), а независимые компоненты разносить по отдельным файлам.

### Подход «по типу ресурса»

Все Deployment в одной папке, все Service в другой, все ConfigMap в третьей. Такой подход удобен, когда у вас много микросервисов и вы хотите быстро найти все ресурсы определённого типа. Но он плохо масштабируется, когда нужно понять, из чего состоит конкретный сервис — приходится прыгать между папками.

### Подход «по сервису/компоненту»

Каждый микросервис или логический компонент живёт в своей папке со всеми своими манифестами. Это наиболее распространённый и рекомендуемый подход, потому что он отвечает на вопрос «что нужно для работы этого сервиса?» одной папкой.

### Подход с окружениями (base + overlays)

Когда одно и то же приложение нужно деплоить в dev, staging и production с разными параметрами, используется структура с базовыми манифестами и наложениями (overlays). Это каноническая структура для Kustomize и Helm.

### Что обязательно, а что нет

Обязательного формата организации не существует — Kubernetes всё равно, как лежат ваши файлы. Ему важно лишь содержимое манифестов. Однако есть негласные конвенции: давать файлам осмысленные имена (обычно `<тип-ресурса>.yaml` или `<имя>-<тип>.yaml`), использовать нумерацию или алфавитный порядок если важен порядок применения, и всегда держать namespace-манифест отдельно, чтобы он применялся первым.

## Манифесты и их назначение

### Namespace

Namespace — это механизм логической изоляции внутри кластера. Он создаёт виртуальную границу, внутри которой живут все ресурсы вашего приложения. Без явного создания namespace ваши ресурсы попадут в `default`, что считается плохой практикой. Namespace позволяет разграничивать ресурсы по командам, проектам или окружениям, применять к ним квоты и сетевые политики. Его манифест обычно применяется первым, до всех остальных ресурсов, потому что остальные ресурсы ссылаются на него в поле `metadata.namespace`. Кроме того, namespace упрощает управление доступом через RBAC — можно дать команде права только на их namespace. Удаление namespace каскадно удаляет все ресурсы внутри него, что удобно для очистки окружений.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: my-app
  labels:
    team: backend
    environment: production
```

### ConfigMap

ConfigMap решает фундаментальную проблему — отделение конфигурации от кода. Вместо того чтобы зашивать настройки в Docker-образ и пересобирать его при каждом изменении конфигурации, вы выносите конфигурацию в отдельный ресурс Kubernetes. ConfigMap может хранить как простые пары ключ-значение, так и целые конфигурационные файлы. Поды могут потреблять ConfigMap двумя способами: через переменные окружения или через монтирование как файловой системы. Важно понимать, что ConfigMap не предназначен для секретных данных — для этого есть Secret. При изменении ConfigMap поды, использующие его через volume mount, получат обновлённые данные автоматически (с задержкой до минуты), а вот переменные окружения не обновляются без перезапуска пода. Это важное архитектурное решение, которое стоит учитывать при проектировании.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: backend-config
  namespace: my-app
data:
  DATABASE_HOST: "postgres.my-app.svc.cluster.local"
  DATABASE_PORT: "5432"
  LOG_LEVEL: "info"
  APP_MODE: "production"
  nginx.conf: |
    server {
      listen 80;
      location / {
        proxy_pass http://backend:8080;
      }
    }
```

### Secret

Secret по своей структуре похож на ConfigMap, но предназначен для хранения чувствительных данных: паролей, токенов, TLS-сертификатов, SSH-ключей. Kubernetes хранит Secret в etcd и может шифровать их at rest, если настроено шифрование. Значения в Secret кодируются в base64 (это не шифрование, а лишь кодирование — важно это понимать). Secret можно подключать к подам так же, как ConfigMap — через переменные окружения или volume mount. Существует несколько типов Secret: `Opaque` для произвольных данных, `kubernetes.io/tls` для TLS-сертификатов, `kubernetes.io/dockerconfigjson` для доступа к приватным Docker-реестрам. На практике для серьёзных проектов часто используют внешние хранилища секретов (HashiCorp Vault, AWS Secrets Manager) с операторами вроде External Secrets Operator, а манифесты Secret не хранят в Git в открытом виде. Для хранения в Git используют SealedSecrets или SOPS.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: backend-secrets
  namespace: my-app
type: Opaque
data:
  DATABASE_PASSWORD: cGFzc3dvcmQxMjM=    # base64
  API_KEY: c2VjcmV0LWFwaS1rZXk=
stringData:                                # можно и без base64
  JWT_SECRET: "my-jwt-secret-value"
```

### Deployment

Deployment — это, пожалуй, самый важный и часто используемый манифест. Он описывает желаемое состояние вашего приложения: какой Docker-образ запускать, сколько реплик должно работать, какие ресурсы выделить, какие порты открыть, как проверять здоровье приложения. Deployment управляет ReplicaSet, который в свою очередь управляет подами. Это двухуровневая абстракция, которая обеспечивает декларативные обновления. Когда вы меняете образ или конфигурацию, Deployment создаёт новый ReplicaSet, постепенно поднимает в нём новые поды и гасит старые — это называется rolling update. Можно настроить стратегию обновления: сколько подов могут быть недоступны одновременно (`maxUnavailable`) и сколько дополнительных подов можно создать (`maxSurge`). Deployment также хранит историю ревизий, позволяя сделать откат к предыдущей версии одной командой. В манифесте Deployment описываются liveness и readiness пробы, requests и limits по CPU и памяти, переменные окружения, volume mounts, affinity/anti-affinity правила, tolerations и множество других параметров.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: my-app
  labels:
    app: backend
    version: v1
spec:
  replicas: 3
  selector:
    matchLabels:
      app: backend
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: backend
        version: v1
    spec:
      serviceAccountName: backend-sa
      containers:
        - name: backend
          image: my-registry/backend:1.2.3
          ports:
            - containerPort: 8080
              protocol: TCP
          env:
            - name: DATABASE_HOST
              valueFrom:
                configMapKeyRef:
                  name: backend-config
                  key: DATABASE_HOST
            - name: DATABASE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: backend-secrets
                  key: DATABASE_PASSWORD
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 10
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
          volumeMounts:
            - name: config-volume
              mountPath: /etc/app/config
      volumes:
        - name: config-volume
          configMap:
            name: backend-config
```

### StatefulSet

StatefulSet решает задачу, с которой Deployment не справляется — управление stateful-приложениями, то есть приложениями, которым важна идентичность и постоянство. Классические примеры: базы данных (PostgreSQL, MySQL), брокеры сообщений (Kafka, RabbitMQ), распределённые хранилища (Elasticsearch, Cassandra). В отличие от Deployment, где поды взаимозаменяемы и получают случайные имена вроде `backend-7d8f9c6b4-xk2lq`, поды StatefulSet получают предсказуемые, упорядоченные имена: `postgres-0`, `postgres-1`, `postgres-2`. Они запускаются и останавливаются строго по порядку. Каждый под может иметь свой собственный PersistentVolume, который сохраняется даже при удалении пода. Кроме того, StatefulSet создаёт для каждого пода стабильную DNS-запись, что позволяет подам находить друг друга по именам. Это критически важно для кластерных баз данных, где нода должна знать адреса остальных нод.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: my-app
spec:
  serviceName: postgres-headless
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:15
          ports:
            - containerPort: 5432
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-secrets
                  key: password
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: fast-ssd
        resources:
          requests:
            storage: 50Gi
```

### Service

Service — это абстракция, которая решает проблему обнаружения сервисов и балансировки нагрузки внутри кластера. Поды эфемерны: они создаются, уничтожаются, их IP-адреса меняются. Service предоставляет стабильный IP-адрес и DNS-имя, за которым скрывается набор подов, отобранных по меткам (labels). Существует несколько типов Service. **ClusterIP** (по умолчанию) — создаёт внутренний IP, доступный только внутри кластера; это основной способ связи между микросервисами. **NodePort** — открывает порт на каждом узле кластера, позволяя обращаться к сервису извне через IP любого узла; используется редко, в основном для простых сценариев или отладки. **LoadBalancer** — провоцирует создание внешнего балансировщика нагрузки у облачного провайдера; это самый простой способ открыть сервис в интернет, но каждый LoadBalancer стоит денег. **Headless Service** (с `clusterIP: None`) — не создаёт виртуального IP, а возвращает DNS-записи для каждого пода напрямую; необходим для StatefulSet, где клиенту нужно обращаться к конкретному поду.

```yaml
# ClusterIP (внутренний)
apiVersion: v1
kind: Service
metadata:
  name: backend
  namespace: my-app
spec:
  type: ClusterIP
  selector:
    app: backend
  ports:
    - port: 80
      targetPort: 8080
      protocol: TCP
---
# Headless для StatefulSet
apiVersion: v1
kind: Service
metadata:
  name: postgres-headless
  namespace: my-app
spec:
  clusterIP: None
  selector:
    app: postgres
  ports:
    - port: 5432
      targetPort: 5432
```

### Ingress

Ingress — это точка входа для HTTP/HTTPS трафика извне кластера. Если Service типа LoadBalancer создаёт по одному балансировщику на каждый сервис (что дорого), то Ingress позволяет маршрутизировать трафик к разным сервисам на основе доменного имени или URL-пути через один единственный внешний IP. По сути, Ingress — это набор правил маршрутизации, а выполняет эти правила Ingress Controller (nginx, Traefik, HAProxy, AWS ALB и т.д.), который нужно установить отдельно. Ingress поддерживает TLS-терминацию, что позволяет централизованно управлять SSL-сертификатами. В связке с cert-manager можно автоматизировать получение и обновление сертификатов от Let's Encrypt. Стоит отметить, что в более новых версиях Kubernetes появился ресурс Gateway API, который считается преемником Ingress и предоставляет более гибкие возможности маршрутизации.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
  namespace: my-app
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - api.example.com
        - app.example.com
      secretName: tls-secret
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: backend
                port:
                  number: 80
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
```

### PersistentVolumeClaim (PVC)

PersistentVolumeClaim — это запрос на выделение постоянного хранилища. Контейнеры по своей природе эфемерны — при перезапуске все данные, записанные в файловую систему контейнера, теряются. PVC решает эту проблему, предоставляя механизм для подключения постоянного тома к поду. PVC работает в связке с PersistentVolume (PV) и StorageClass. StorageClass определяет, какой тип хранилища использовать (SSD, HDD, сетевой диск). PVC запрашивает определённый объём хранилища и режим доступа (`ReadWriteOnce` — том доступен одному узлу для чтения и записи, `ReadOnlyMany` — многим узлам только для чтения, `ReadWriteMany` — многим узлам для чтения и записи). Динамический provisioning позволяет автоматически создавать PV при появлении PVC, что устраняет необходимость ручного создания томов администратором. Для StatefulSet PVC создаются автоматически через `volumeClaimTemplates`, для Deployment PVC описывается отдельным манифестом.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: media-storage
  namespace: my-app
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard
  resources:
    requests:
      storage: 20Gi
```

### HorizontalPodAutoscaler (HPA)

HPA автоматически масштабирует количество реплик Deployment или StatefulSet на основе наблюдаемых метрик. Идея проста: вы задаёте целевую загрузку (например, 70% CPU), и HPA добавляет поды, когда нагрузка превышает порог, и убирает лишние, когда нагрузка снижается. Это позволяет эффективно использовать ресурсы кластера — не держать избыточные поды в спокойное время и автоматически увеличивать мощность при пиковых нагрузках. HPA v2 поддерживает масштабирование не только по CPU и памяти, но и по пользовательским метрикам (количество запросов в секунду, длина очереди сообщений и т.д.) через Metrics API. Для работы HPA необходим установленный metrics-server в кластере. Важно правильно настроить `minReplicas` и `maxReplicas`, а также `behavior` — скорость масштабирования вверх и вниз, чтобы избежать «флэппинга» (постоянного добавления/удаления реплик).

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: backend-hpa
  namespace: my-app
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: backend
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Pods
          value: 1
          periodSeconds: 120
```

### ServiceAccount

ServiceAccount определяет идентичность, от имени которой работают поды. По умолчанию каждый под получает ServiceAccount `default`, но это плохая практика с точки зрения безопасности — принцип наименьших привилегий требует, чтобы каждый компонент имел только те права, которые ему необходимы. ServiceAccount нужен, когда приложению требуется взаимодействовать с API Kubernetes (например, оператор, который создаёт ресурсы) или когда нужно использовать механизмы аутентификации облачных провайдеров (IAM Roles for Service Accounts в AWS, Workload Identity в GCP). ServiceAccount связывается с подом через поле `serviceAccountName` в спецификации пода. Kubernetes автоматически монтирует токен ServiceAccount в под, который приложение может использовать для аутентификации в API-сервере.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: backend-sa
  namespace: my-app
  annotations:
    # Пример для AWS IRSA
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/backend-role
automountServiceAccountToken: true
```

### Role и RoleBinding (RBAC)

Role и RoleBinding — это механизм контроля доступа на уровне namespace. Role определяет набор разрешений: какие действия (verbs: get, list, watch, create, update, delete) можно совершать с какими ресурсами (pods, services, configmaps и т.д.). RoleBinding привязывает Role к конкретному субъекту — ServiceAccount, пользователю или группе. Для кластерного уровня (без привязки к namespace) существуют ClusterRole и ClusterRoleBinding. Это критически важная часть безопасности: без правильно настроенного RBAC любой под с доступом к API-серверу может делать что угодно в кластере. На практике RBAC нужен в первую очередь для операторов, CI/CD систем и любых приложений, которые взаимодействуют с Kubernetes API.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: backend-role
  namespace: my-app
rules:
  - apiGroups: [""]
    resources: ["configmaps", "secrets"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: backend-rolebinding
  namespace: my-app
subjects:
  - kind: ServiceAccount
    name: backend-sa
    namespace: my-app
roleRef:
  kind: Role
  name: backend-role
  apiGroup: rbac.authorization.k8s.io
```

### NetworkPolicy

NetworkPolicy — это файрвол на уровне подов. По умолчанию в Kubernetes все поды могут общаться со всеми подами без ограничений — это удобно для разработки, но неприемлемо для продакшена. NetworkPolicy позволяет определить, какие поды могут общаться с какими, на каких портах и протоколах. Политики работают по принципу белого списка: как только для пода появляется хотя бы одна NetworkPolicy, весь трафик, не разрешённый явно, блокируется. Можно ограничивать как входящий (ingress), так и исходящий (egress) трафик. Например, можно разрешить фронтенду обращаться только к бэкенду, бэкенду — только к базе данных, а базе данных — не общаться ни с чем, кроме бэкенда. Для работы NetworkPolicy необходим сетевой плагин (CNI), который их поддерживает: Calico, Cilium, Weave Net. Стандартный kubenet NetworkPolicy не поддерживает.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-netpol
  namespace: my-app
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
        - namespaceSelector:
            matchLabels:
              name: monitoring
      ports:
        - protocol: TCP
          port: 8080
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: postgres
      ports:
        - protocol: TCP
          port: 5432
    - to:   # DNS
        - namespaceSelector: {}
      ports:
        - protocol: UDP
          port: 53
```

### ResourceQuota

ResourceQuota устанавливает ограничения на суммарное потребление ресурсов в namespace. Это защитный механизм на уровне кластера, который предотвращает ситуацию, когда одна команда или проект «съедает» все ресурсы кластера, оставляя остальных без вычислительных мощностей. ResourceQuota может ограничивать: суммарное количество CPU и памяти (requests и limits), количество объектов определённого типа (поды, сервисы, PVC), суммарный объём хранилища. Когда quota исчерпана, новые ресурсы создать нельзя — Kubernetes вернёт ошибку. Это особенно полезно в мультитенантных кластерах, где разные команды делят один кластер.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: my-app
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"
    services: "10"
    persistentvolumeclaims: "5"
    requests.storage: 100Gi
```

### LimitRange

LimitRange дополняет ResourceQuota, работая на уровне отдельных подов и контейнеров, а не namespace в целом. Он задаёт значения по умолчанию и границы для ресурсов контейнеров. Если разработчик забыл указать requests и limits в своём Deployment (что случается часто), LimitRange подставит значения по умолчанию. Если указал слишком большие или слишком маленькие — LimitRange отклонит создание пода. Это страховочная сетка, которая не позволяет запустить контейнер без ограничений ресурсов (что может привести к «шумному соседу», забирающему все ресурсы узла) или с неоправданно большими запросами.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: resource-limits
  namespace: my-app
spec:
  limits:
    - type: Container
      default:
        cpu: "500m"
        memory: "256Mi"
      defaultRequest:
        cpu: "100m"
        memory: "128Mi"
      max:
        cpu: "2"
        memory: "2Gi"
      min:
        cpu: "50m"
        memory: "64Mi"
    - type: PersistentVolumeClaim
      max:
        storage: 50Gi
      min:
        storage: 1Gi
```

### PodDisruptionBudget (PDB)

PodDisruptionBudget — это механизм обеспечения доступности при плановых (voluntary) прерываниях: обновление узлов, масштабирование кластера, drain ноды для обслуживания. PDB гарантирует, что в любой момент времени определённое количество подов вашего приложения будет работать. Без PDB операция `kubectl drain` может одновременно выселить все поды вашего приложения с узла, вызвав даунтайм. PDB задаёт либо `minAvailable` (минимальное количество доступных подов), либо `maxUnavailable` (максимальное количество недоступных подов). Kubernetes не нарушит PDB при плановых операциях. Однако PDB не защищает от аварийных ситуаций — если узел внезапно упал, PDB не поможет; для этого нужны реплики на разных узлах через pod anti-affinity.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: backend-pdb
  namespace: my-app
spec:
  minAvailable: 2        # или maxUnavailable: 1
  selector:
    matchLabels:
      app: backend
```

### CronJob и Job

Job запускает одну или несколько подов для выполнения конечной задачи и следит за их успешным завершением. Если под упал, Job перезапустит его. Это полезно для миграций базы данных, batch-обработки, генерации отчётов. CronJob — это Job, запускаемый по расписанию в формате cron. Он нужен для периодических задач: очистка устаревших данных, отправка email-рассылок, создание бэкапов. CronJob создаёт объекты Job по расписанию, а каждый Job создаёт поды. Важно настраивать `concurrencyPolicy` (что делать, если предыдущий Job ещё не завершился), `successfulJobsHistoryLimit` и `failedJobsHistoryLimit` (сколько завершённых/упавших Job'ов хранить), а также `activeDeadlineSeconds` (таймаут выполнения).

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup
  namespace: my-app
spec:
  schedule: "0 2 * * *"       # каждый день в 2:00
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      activeDeadlineSeconds: 3600
      backoffLimit: 3
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: my-registry/db-backup:latest
              env:
                - name: DB_PASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: postgres-secrets
                      key: password
              volumeMounts:
                - name: backup-storage
                  mountPath: /backups
          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: backup-pvc
```

### DaemonSet

DaemonSet гарантирует, что на каждом узле (или на определённом подмножестве узлов) кластера запущен ровно один экземпляр пода. Когда новый узел добавляется в кластер, DaemonSet автоматически запускает на нём под; когда узел удаляется — под тоже удаляется. Классические сценарии использования: сборщики логов (Fluentd, Filebeat), агенты мониторинга (Prometheus Node Exporter, Datadog Agent), сетевые плагины (Calico, Cilium), агенты безопасности (Falco). DaemonSet не используется для обычных приложений — он именно для инфраструктурных компонентов, которые должны присутствовать на каждом узле.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
  namespace: kube-system
spec:
  selector:
    matchLabels:
      app: fluentd
  template:
    metadata:
      labels:
        app: fluentd
    spec:
      tolerations:
        - key: node-role.kubernetes.io/control-plane
          effect: NoSchedule
      containers:
        - name: fluentd
          image: fluent/fluentd:v1.16
          resources:
            limits:
              memory: 200Mi
            requests:
              cpu: 100m
              memory: 200Mi
          volumeMounts:
            - name: varlog
              mountPath: /var/log
      volumes:
        - name: varlog
          hostPath:
            path: /var/log
```

### PriorityClass

PriorityClass определяет приоритет подов при планировании и при нехватке ресурсов. Когда в кластере заканчиваются ресурсы, планировщик может вытеснить (evict) поды с более низким приоритетом, чтобы разместить поды с более высоким. Это позволяет гарантировать, что критически важные сервисы (продакшен, платёжная система) всегда получат ресурсы за счёт менее важных (batch-задачи, dev-окружения). Значение priority — целое число; чем больше, тем выше приоритет. PriorityClass — кластерный ресурс, не привязанный к namespace.

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
description: "Для критически важных production-сервисов"
```
