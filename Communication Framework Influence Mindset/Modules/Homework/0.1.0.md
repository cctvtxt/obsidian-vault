Подход 1 (наиболее чистый Git Flow, рекомендую)
Scaffold делается напрямую в develop как стартовая точка проекта. Это исключение из правил «не коммить в develop» обосновано: до того как develop «отпочковался» от main, нет смысла плодить ветки.
git checkout main
git checkout -b develop
# коммитишь scaffold прямо в develop
_chore(root): monorepo, docker, env, proto, services bootstrap_
git push -u origin develop
Только после того как develop есть и включает scaffold, начинаешь нормальный Git Flow: от develop создаёшь feature/registration, feature/login и т.д.
Имя ветки — develop (не feature/*). Названия коммитов — build():, chore():, feat(common): по conventional commits.
Подход 2 (всё-таки через ветку)
Если хочешь строго через PR/ревью:
git checkout -b develop
git push -u origin develop

git checkout -b chore/scaffold
# работаешь
git checkout develop
git merge --no-ff chore/scaffold
git branch -d chore/scaffold
Используй префикс chore/ или build/, не feature/.
Мой совет: на этом этапе бери Подход 1. Scaffold — единственная работа, разумно вести её прямо в develop, не усложняя лишними суррогатными ветками. Дальше (registration, login...) — только через feature/.

feat(user-service): add prisma schema with user model

feat(api-gateway): bootstrap nestjs with fastify and swagger

```

### CI

test(auth-service): add unit tests for password and login flows

test(token-service): add unit tests for token lifecycle

test(api-gateway): add e2e tests for all account endpoints

```

  

### Release

  

Ветка `release/0.1.0`, вливается в main и обратно в dev.

  

```

fix(root): resolve final env and startup issues

docs(root): add final setup guide and review checklist

docs(root): add adr for git flow and architecture decisions

chore(root): prepare version metadata for first delivery

```

  

```bash

git checkout dev && git pull origin dev

git checkout -b release/0.1.0 && git push -u origin release/0.1.0

# MR release/0.1.0 → main

git checkout dev && git merge origin/main && git push origin dev

```
