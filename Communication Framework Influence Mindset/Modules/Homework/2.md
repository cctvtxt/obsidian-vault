# feature/balance-management
1. Внедрение нового поля баланса пользователям
2. Использование транзакции для перевода с одного баланса пользователя на другой
3. Реализация функциональной возможности обнуления баланса всех пользователей
4. Добавить повторяемую джобу для обнуления баланса всех пользователей


Ты прав — для конкретно этой операции «обнулить всем balance» один запрос действительно возможен и был бы правильным техническим решением:
UPDATE "user" SET balance = 0 WHERE "deletedAt" IS NULL;
И да, это не блокирует event loop (I/O асинхронный). Но есть нюанс: клиент всё равно ждёт ответа. «БД асинхронна» означает лишь, что запрос не блокирует Node на время ожидания, а await всё равно держит HTTP-ответ до завершения. Если таблица огромная — запрос идёт 30 секунд, и клиент висит 30 секунд или ловит timeout.
Поэтому тут честный ответ такой: задача учебная — она учит паттерну «очередь», а не потому что один UPDATE не справился бы. На практике очередь оправдана, когда операцию нельзя выразить одним запросом или она слишком тяжёлая:
- Не выражается одним SQL: пересчёт баланса на основе транзакций, вызов внешнего API/отправка письма на каждого юзера, размножение файлов, каскадные действия.
- Огромная таблица: один UPDATE берёт row-локи на миллионы строк, блокируя параллельные записи и раздувая таблицу (bloat). Тогда правильнее чанками по 1000 через worker с ограниченным concurrency.
- Надёжность: retry при падении посреди работы, мониторинг прогресса, дашборд Bull.
- Планировщик: задача «каждые 10 минут» — это repeatable job в Bull.
- Развязка ответа и исполнения: клиент получает «принято» мгновенно, а не ждёт завершения тяжелой работы.

План B: Makefile (локальная подготовка) + GitHub Actions (публикация в CI)
Модель
- Makefile делает всё, что должно быть в git: бамп версии common/package.json, синхронизация lockfile, коммит, тег, push, триггер воркфлоу.
- GitHub Actions (workflow_dispatch, без on: push) делает безопасную публикацию: чистый checkout → install → pnpm gen → build → pnpm publish с NODE_AUTH_TOKEN из GitHub Secrets.
- Версия берётся из common/package.json (которую забампил Makefile и запушил перед триггером) — никакой гонки с registry, никакого commit-back из CI.
Фаза 1 — подготовка common
common/package.json:
- "name": "@org-18247/common", "version": "1.0.0", "type": "module"
- "main": "./dist/index.js", "types": "./dist/index.d.ts" (+ создать common/index.ts с re-export config/prisma/redis)
- "files": ["dist", "contracts/proto", "README.md", "LICENSE"]
- "scripts": { "build": "tsc -p tsconfig.build.json", "prepack": "pnpm run build" }
- "publishConfig": { "access": "public", "registry": "https://registry.npmjs.org" }
- exports: ./configs/*, ./modules/*, ./filters/*, ./enums/*, ./contracts/generated/*, ./contracts/proto/*, ./package.json
- peerDependencies: @nestjs/*, @prisma/client, rxjs, reflect-metadata, class-transformer, class-validator — явные версии
- dependencies: joi, ioredis
- Все версии явные, без catalog: — самодостаточный пакет
common/tsconfig.build.json: extends ./tsconfig.json, exclude: ["eslint.config.mjs"].
common/README.md + common/LICENSE (ISC).
Фаза 2 — Makefile
BUMP ?= patch

.PHONY: publish-common
publish-common:
	cd common && npm version $(BUMP) --no-git-tag-version
	pnpm install
	git add common/package.json pnpm-lock.yaml
	git commit -m "chore(release): @org-18247/common"
	git tag common-v$$(node -p "require('./common/package.json').version")
	git push origin $$(git branch --show-current) --tags
	gh workflow run publish-common.yml --ref $$(git branch --show-current)
Шаги: бамп версии → sync lockfile → коммит версии+lockfile → тег common-vX.Y.Z → push ветки и тегов → gh workflow run (публикацию делает CI).
Фаза 3 — GitHub Actions
.npmrc (корень, коммитится):
//registry.npmjs.org/:_authToken=${NODE_AUTH_TOKEN}
.github/workflows/publish-common.yml:
name: publish-common
on:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: pnpm/action-setup@v4
        with: { version: 11 }
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          registry-url: https://registry.npmjs.org
      - run: pnpm install --frozen-lockfile
      - run: pnpm gen
      - run: pnpm --filter @org-18247/common build
      - run: pnpm --filter @org-18247/common publish --no-git-checks
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
Почему workflow_dispatch без on: push: публикация только по команде (make publish-common или кнопка в UI), пуш в develop не триггерит (его позже заберёт Docker Hub воркфлоу). gh workflow run физически требует наличие этого файла — без него команда не найдёт воркфлоу.

Замечания / риски
- Секрет NPM_TOKEN в GitHub Secrets; токен без 2FA/OTP (иначе CI publish упадёт).
- common/dist и common/contracts/generated в .gitignore → pnpm gen в CI обязателен до build (есть).
- Первая публикация уйдёт как 1.0.0 (из package.json), дальше бампы через Makefile.
- Push → publish: воркфлоу чекаутит уже закоммиченный реф, поэтому tarball соответствует коду в git.
- Если pnpm publish упадёт (версия занята) — CI просто покажет ошибку, в git останется тег common-vX.Y.Z; бампишь ещё раз и перезапускаешь.
