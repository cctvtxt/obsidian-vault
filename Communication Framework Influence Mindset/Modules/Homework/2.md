## Ответы по пунктам

  

### 1. Уведомления: как правильно развязать

  

Ключевой принцип: **media-service вообще не знает про клиентов и SSE**. Он публикует доменные события в очередь — и всё. Кто их потребляет — вопрос конфигурации, а не архитектуры:

  

```

media-service worker ──publish──> BullMQ (media.events)

                                        │

              ┌─────────────────────────┴──────────────┐

              ▼ потребитель событий (заменяемый)       │

     сегодня: api-gateway ──SSE──> клиент              │

     завтра: notification-service ──SSE──> клиент      │

```

  

Событие нейтральное: `{event, key, ownerAccountId, status}`. Потребитель держит реестр `accountId → SSE-подключения` и рассылает. Хочешь вынести в отдельный notification-service позже — просто переносишь consumer'а, media-service не меняется ни строчкой. Это и есть «обобщённость» — граница проходит по очереди, а не по вызову.

  

### 2. ConfirmUpload

  

Добавляю в контракт: `ConfirmUpload(key) → FileMetadata` — синхронный HeadObject-верификатор рядом с асинхронным вебхуком. Worker идемпотентен (проверяет status-tag), гонки confirm/webhook не страшны.

  

### 3. ТЗ vs наш план: что корректировать

  

ТЗ **не противоречит бизнес-требованиям, но противоречит собственному твоему решению** («отвязать gateway от нагрузки») в механике. Механику ТЗ (multipart → FileInterceptor → кастомный pipe → бэкенд льёт в S3) мы осознанно заменяем, а всё содержательное ложится 1:1:

## Assistant

  

| ТЗ | Наша реализация |

|---|---|

| jpeg/png ≤ 10 МБ | Профиль `avatar: {allowedMimes: [image/jpeg, image/png], maxSizeBytes: 10MB}` — строка декларативного конфига purpose-профилей |

| multipart + FileInterceptor | Presigned POST: байты идут клиент → MinIO напрямую, бэкенд трафик не трогает |

| Кастомный pipe (тип/размер) | Та же валидация, но раньше и надёжнее: policy-условия подписываются в интент (`content-type` whitelist + `content-length-range`) + сниффинг магических байтов в worker'е постфактум |

| «Храним имя файла, не путь» | Храним только key `avatar/{ownerId}/{fileId}`, URL собирается на лету через `GetDownloadUrl` — отвязка от домена даже полнее, чем требует ТЗ |

| @aws-sdk/client-s3 | Тот же v3 + `@aws-sdk/s3-request-presigner` |

  

## Маппинг сущности avatars (ТЗ → потребители)

  

- **Avatars живут в user-service** (решение «attach в потребителях»): Prisma-модель `Avatar {id, accountId, fileKey, isActive, createdAt (= addedAt из ТЗ), deletedAt}`

- **До 5 активных** — квота в attach-логике user-service

- **Soft delete** — `isActive=false + deletedAt`; сам объект в S3 остаётся до cleanup (lifecycle rule / периодическая задача — опциональный этап)

- **«Только своя аватарка»** — двойная защита: ownerId берётся из JWT при создании интента (ключ уже содержит владельца), плюс attach проверяет `fileKey` начинается с `avatar/{accountId}/`

- **Роуты ТЗ**: `POST /users/me/avatars` (attach), `DELETE /users/me/avatars/:id` (soft delete). Полный клиентский сценарий: intent → PUT в MinIO → вебхук/SSE → attach → готово

  

## Вердикт по корректировке плана

  

План **корректировать не нужно** — ТЗ встраивается как первый реальный потребитель платформы (сценарий «аватары» в user-service). От механики ТЗ осознанно отходим: она противоречила твоему же требованию развязать gateway от трафика, а все содержательные требования ТЗ выполняются. Единственная цена — если работу оценивает ментор, ожидающий буквально `FileInterceptor`, это вопрос процесса, не архитектуры.



## Актуализированный план этапов

  

1. **Контракты**: `media.proto` (+`ConfirmUpload`), типы событий очереди в common, расширение user.proto (attach/delete/list avatars RPC)

2. **s3-client** (shared): async-рефакторинг, `registerAsync`+env, генератор presigned POST (policy: mimes, size, меты), presigned GET, head/delete/tags, тесты

3. **docker-compose**: minio + mc sidecar (бакеты, webhook), `.env.example`

4. **media-service**: гибрид gRPC + HTTP-webhook + BullMQ worker (HeadObject, сниффинг mime, status-tag, publish события); purpose-профили — конфиг-мапа

5. **api-gateway**: `modules/media` (intent/confirm/download-url), SSE-hub поверх QueueEvents (фильтрация по accountId), аватарные роуты

6. **user-service**: Prisma `Avatar`, attach с квотой и ревалидацией через `GetFileMetadata`, soft delete

7. **Прод-обвязка**: bake/prod-compose/k8s

  

По SSE-hub рекомендую начать внутри api-gateway (auth уже там, минус сервис), вынос в notification-service позже — перенос одного consumer'а благодаря границе по очереди.
