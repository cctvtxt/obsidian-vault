Вот сжатая, практическая выжимка без лишнего — что именно нужно сделать, чтобы всё заработало.

## 1. Логирование (pino)

- Использовать `nestjs-pino`
    
- Формат: JSON → stdout (1 лог = 1 строка)
    
- Базовые поля:
    
    - `timestamp, level, service, env, message`
        
- Контекстные поля (авто):
    
    - `traceId, spanId, operationId`
        
- HTTP/gRPC поля:
    
    - `method, path, grpcService, grpcMethod, statusCode, durationMs, error`
        

Ключ:

- `message` — короткий и стабильный
    
- всё остальное — в JSON-полях
    

---

## 2. Request Context (ядро всей схемы)

- `AsyncLocalStorage`
    
- Хранит:
    
    - `traceId`
        
    - `spanId`
        
    - `operationId`
        

Используется:

- логгером (через `mixin`)
    
- интерцепторами
    
- любым кодом внутри запроса
    

---

## 3. HTTP вход (Gateway / edge)

Сделать `NestInterceptor`:

Что делает:

- читает `traceparent` из headers
    
- если нет → генерит
    
- генерит `operationId` (или берёт из `x-operation-id`)
    
- кладёт всё в `AsyncLocalStorage`
    
- логирует:
    
    - `request started`
        
    - `request completed / failed`
        

Важно:

- возвращает `operationId` в response header
    

---

## 4. gRPC прокидывание контекста

## Client interceptor

- берёт из `AsyncLocalStorage`:
    
    - `traceparent`
        
    - `operationId`
        
- кладёт в `metadata`
    

## Server interceptor

- читает metadata
    
- восстанавливает:
    
    - `traceId`
        
    - `spanId`
        
    - `operationId`
        
- кладёт в `AsyncLocalStorage`
    

Важно:

- `traceId/spanId` → только metadata (НЕ protobuf)
    
- `operationId` → можно в protobuf, если нужен бизнесу

Сделать `@yourorg/common`:

Внутри:

- `RequestContext` (ALS)
    
- `LoggerModule` (pino + mixin)
    
- `HttpTraceInterceptor`
    

Подключение:

- `imports: [CommonModule]` в каждом сервисе

## 6. Авто-инъекция trace в логи

Через `pino.mixin()`:

Если есть контекст:

- добавляет `traceId, spanId, operationId`
    

Если нет (startup/shutdown):

- ничего не добавляет (это правильно)

## 7. Lifecycle логирование (НЕ request)

В `main.ts`:

Логировать:

- `http server starting`
    
- `http server listening`
    
- `shutdown signal`
    
- `graceful shutdown done/failed`
    

Важно:

- без `traceId` (это не request)

## 8. Loki интеграция (через Docker driver)

В `docker-compose`:

- driver: `loki`
    
- labels:
    
    - `service`
        
    - `env`
        

Важно:

- НЕ использовать labels для:
    
    - `traceId`
        
    - `userId`
        
    - `statusCode`
        
- они остаются в JSON

## 9. LogQL (как реально искать)

Примеры:

- ошибки:  
    `{service="api-gateway"} | json | level="error"`
    
- 5xx:  
    `{service="api-gateway"} | json | statusCode >= 500`
    
- полный trace:  
    `{env="prod"} | json | traceId="..."`

## 10. Критичные правила (не нарушать)

- Один traceId на весь request chain (HTTP → gRPC → …)
    
- Не класть traceId в protobuf
    
- Не делать высокую кардинальность в Loki labels
    
- Всегда прокидывать context через AsyncLocalStorage
    
- `message` не должен содержать динамику (IDs, payload)

## Минимальный end-to-end поток

1. HTTP запрос приходит в Gateway
    
2. Interceptor:
    
    - создаёт/читает `traceparent`
        
    - создаёт `operationId`
        
3. Всё кладётся в ALS
    
4. Логи автоматически получают trace поля
    
5. gRPC client:
    
    - кладёт context в metadata
        
6. downstream сервис:
    
    - читает metadata
        
    - продолжает trace
        
7. Loki:
    
    - хранит JSON
        
8. Grafana:
    
    - `traceId` → виден весь путь запроса

## Суть для реализации

**Логгер:** pino (не winston) — быстрее, нативно JSON, подходит для high-load микросервисов.

**Трассировка:** OpenTelemetry + единый trace context (traceparent) между HTTP и gRPC.

### Формат логов

JSON в stdout, одна запись — одна строка.

Базовые поля: `timestamp, level, service, env, traceId, spanId, operationId, message` Доп. поля: `method, path, grpcService, grpcMethod, statusCode, durationMs, error`

```json
{
  "timestamp": "2026-06-28T12:00:00.123Z",
  "level": "info",
  "service": "api-gateway",
  "env": "prod",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "spanId": "00f067aa0ba902b7",
  "operationId": "req-8c9f5d",
  "message": "request completed",
  "method": "GET",
  "path": "/users/42",
  "statusCode": 200,
  "durationMs": 34
}
```

Правило: `message` короткий и стабильный, всё остальное — в полях. Высококардинальные данные (userId, query params, body) — **не** в Loki labels, только в теле лога. В Loki labels — только `service, env, level, transport`.

### Как передавать trace context

|Что|Куда|
|---|---|
|traceId, spanId, traceparent|HTTP headers / gRPC metadata|
|operationId / commandId (бизнесовый)|gRPC metadata + protobuf, если нужен доменной логике/аудиту/идемпотентности|

Поток:

1. Gateway получает HTTP request → читает `traceparent`, если нет — создаёт новый.
2. При вызове gRPC — кладёт `traceparent` в metadata.
3. Внутренний сервис читает metadata → продолжает trace → пишет тот же `traceId` в свои логи.

**Protobuf не трогаем** для traceId/spanId — это транспортный контекст, ему место в metadata. В protobuf добавляем только свой `operationId`, если он нужен как часть контракта (хранение в БД, ответ клиенту, идемпотентность).

### План внедрения

1. Подключить pino в каждый сервис, унифицировать JSON-схему логов.
2. Nest middleware/interceptor для `traceparent` + `operationId`.
3. gRPC client interceptor — копирует `traceparent` и `operationId` в metadata.
4. gRPC server interceptor — читает metadata, кладёт в request context/logger context.
5. Loki labels: только `service, env, level, transport`.

## Common-сущность (общий пакет для всех сервисов)

Делаем `libs/common` (или npm-пакет `@yourorg/common`), который импортируют все сервисы. В нём три части: контекст, логгер, HTTP-интерцептор.

### 1. Контекст запроса (AsyncLocalStorage)

```ts
// common/src/context/request-context.ts
import { AsyncLocalStorage } from 'async_hooks';

export interface RequestContext {
  traceId: string;
  spanId?: string;
  operationId: string;
}

export const requestContextStorage = new AsyncLocalStorage<RequestContext>();

export function getRequestContext(): RequestContext | undefined {
  return requestContextStorage.getStore();
}
```

### 2. Логгер (pino + автоматическая инъекция traceId/operationId)

```ts
// common/src/logger/logger.module.ts
import { Module } from '@nestjs/common';
import { LoggerModule as PinoLoggerModule } from 'nestjs-pino';
import { getRequestContext } from '../context/request-context';

@Module({
  imports: [
    PinoLoggerModule.forRoot({
      pinoHttp: {
        level: process.env.LOG_LEVEL ?? 'info',
        base: {
          service: process.env.SERVICE_NAME,
          env: process.env.NODE_ENV,
        },
        // подмешивает traceId/operationId в каждую запись, если есть активный контекст
        mixin() {
          const ctx = getRequestContext();
          return ctx
            ? { traceId: ctx.traceId, spanId: ctx.spanId, operationId: ctx.operationId }
            : {};
        },
        timestamp: () => `,"timestamp":"${new Date().toISOString()}"`,
      },
    }),
  ],
  exports: [PinoLoggerModule],
})
export class CommonLoggerModule {}
```

Важный момент: `mixin()` сам решает, добавлять trace-поля или нет. Если лог пишется вне HTTP/gRPC запроса (например, при старте сервера) — контекста нет, и эти поля просто не появятся. Это и нужно — не подделывать traceId там, где трейса физически не существует.

### 3. HTTP-интерцептор (генерит/читает traceparent + operationId, кладёт в контекст)

```ts
// common/src/interceptors/http-trace.interceptor.ts
import { Injectable, NestInterceptor, ExecutionContext, CallHandler } from '@nestjs/common';
import { Observable } from 'rxjs';
import { tap } from 'rxjs/operators';
import { randomUUID, randomBytes } from 'crypto';
import { PinoLogger } from 'nestjs-pino';
import { requestContextStorage } from '../context/request-context';

const TRACE_HEADER = 'traceparent';
const OPERATION_ID_HEADER = 'x-operation-id';

@Injectable()
export class HttpTraceInterceptor implements NestInterceptor {
  constructor(private readonly logger: PinoLogger) {
    this.logger.setContext('http');
  }

  intercept(ctx: ExecutionContext, next: CallHandler): Observable<any> {
    const req = ctx.switchToHttp().getRequest();
    const res = ctx.switchToHttp().getResponse();

    const traceparent = req.headers[TRACE_HEADER] ?? generateTraceparent();
    const operationId = req.headers[OPERATION_ID_HEADER] ?? randomUUID();
    const { traceId, spanId } = parseTraceparent(traceparent);

    res.setHeader(OPERATION_ID_HEADER, operationId);
    const start = Date.now();

    return requestContextStorage.run({ traceId, spanId, operationId }, () => {
      this.logger.info({ method: req.method, path: req.url }, 'request started');

      return next.handle().pipe(
        tap({
          next: () =>
            this.logger.info(
              { method: req.method, path: req.url, statusCode: res.statusCode, durationMs: Date.now() - start },
              'request completed',
            ),
          error: (err) =>
            this.logger.error(
              { method: req.method, path: req.url, durationMs: Date.now() - start, error: err.message },
              'request failed',
            ),
        }),
      );
    });
  }
}

function generateTraceparent(): string {
  return `00-${randomBytes(16).toString('hex')}-${randomBytes(8).toString('hex')}-01`;
}

function parseTraceparent(tp: string) {
  const [, traceId, spanId] = tp.split('-');
  return { traceId, spanId };
}
```

### 4. Сборка в один глобальный модуль

```ts
// common/src/common.module.ts
import { Global, Module } from '@nestjs/common';
import { APP_INTERCEPTOR } from '@nestjs/core';
import { CommonLoggerModule } from './logger/logger.module';
import { HttpTraceInterceptor } from './interceptors/http-trace.interceptor';

@Global()
@Module({
  imports: [CommonLoggerModule],
  providers: [{ provide: APP_INTERCEPTOR, useClass: HttpTraceInterceptor }],
  exports: [CommonLoggerModule],
})
export class CommonModule {}
```

Каждый сервис просто делает `imports: [CommonModule]` в своём `AppModule` — и логгер, и трейсинг подключены одинаково везде.

## Логирование перезапуска HTTP-сервера

Перезапуск — это всегда **graceful shutdown + новый старт процесса**. Логируем обе стороны явно, без подделки traceId (его здесь просто нет — это не запрос, а lifecycle-событие).

```ts
// main.ts
import { NestFactory } from '@nestjs/core';
import { Logger } from 'nestjs-pino';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule, { bufferLogs: true });
  app.useLogger(app.get(Logger));
  app.enableShutdownHooks(); // обязательно для onApplicationShutdown

  const logger = app.get(Logger);
  logger.setContext('bootstrap');

  const port = process.env.PORT ?? 3000;

  logger.info({ port }, 'http server starting');
  await app.listen(port);
  logger.info({ port }, 'http server listening');

  process.on('SIGTERM', () => shutdown(app, logger, 'SIGTERM'));
  process.on('SIGINT', () => shutdown(app, logger, 'SIGINT'));
}

async function shutdown(app: any, logger: Logger, signal: string) {
  logger.warn({ signal }, 'http server received shutdown signal');
  try {
    await app.close(); // здесь же отработают onApplicationShutdown во всех модулях
    logger.info({ signal }, 'http server stopped gracefully');
    process.exit(0);
  } catch (err) {
    logger.error({ signal, error: (err as Error).message }, 'http server shutdown failed');
    process.exit(1);
  }
}

bootstrap();
```

Что получится в Loki при перезапуске (k8s rolling restart / pm2 reload):

```json
{"timestamp":"2026-06-28T12:00:00.000Z","level":"warn","service":"api-gateway","env":"prod","message":"http server received shutdown signal","signal":"SIGTERM"}
{"timestamp":"2026-06-28T12:00:00.150Z","level":"info","service":"api-gateway","env":"prod","message":"http server stopped gracefully","signal":"SIGTERM"}
{"timestamp":"2026-06-28T12:00:01.020Z","level":"info","service":"api-gateway","env":"prod","message":"http server starting","port":3000}
{"timestamp":"2026-06-28T12:00:01.080Z","level":"info","service":"api-gateway","env":"prod","message":"http server listening","port":3000}
```

Обратите внимание — `traceId`/`operationId` тут нет вообще, и это правильно: эти поля живут только внутри `requestContextStorage.run(...)`, а старт/стоп процесса происходит вне любого запроса.

Если нужно логировать закрытие конкретных ресурсов (gRPC-клиенты, DB pool) при шатдауне — добавляй `OnApplicationShutdown` в нужный провайдер:

```ts
@Injectable()
export class GrpcClientService implements OnApplicationShutdown {
  constructor(private readonly logger: PinoLogger) {
    this.logger.setContext('grpc-client');
  }

  async onApplicationShutdown(signal?: string) {
    this.logger.info({ signal }, 'closing grpc client connections');
    await this.client.close();
  }
}
```

Это даст более детальную картину при ресурсо-тяжёлых сервисах — видно не просто "сервер остановился", а что конкретно закрывалось и в каком порядке.

## Нужен ли Loki Docker Driver

Раз у тебя уже все сервисы пишут структурированный JSON в stdout (как договорились ранее) — driver просто берёт этот поток и пушит в Loki по HTTP. Дополнительный код в сервисах не нужен, это чисто инфраструктурная настройка на уровне Docker.

⚠️ Важная оговорка: у driver исторически были проблемы с надёжностью — если Loki временно недоступен, логи могут теряться без буферизации (зависит от версии и режима). Для прод-критичных логов многие переходят на Promtail/Alloy именно из-за этого. Для старта и среднего масштаба driver — нормальный выбор.

## Как подключить

### 1. Установить плагин на хосте (один раз, до `docker-compose up`)

```bash
docker plugin install grafana/loki-docker-driver:latest --alias loki --grant-all-permissions
```

Compose сам плагин не ставит — это шаг провижининга хоста (Ansible/Terraform/ручной запуск).

### 2. docker-compose.yml

```yaml
version: "3.8"

services:
  loki:
    image: grafana/loki:3.0.0
    ports:
      - "3100:3100"
    command: -config.file=/etc/loki/local-config.yaml
    networks: [observability]
    # ВАЖНО: loki и grafana НЕ используют loki-driver сами на себя —
    # иначе при падении Loki теряются и его собственные логи о падении.
    # Оставляем им json-file (дефолт).

  grafana:
    image: grafana/grafana:11.0.0
    ports:
      - "3000:3000"
    environment:
      - GF_AUTH_ANONYMOUS_ENABLED=true
    networks: [observability]
    depends_on: [loki]

  api-gateway:
    build: ./services/api-gateway
    logging:
      driver: loki
      options:
        loki-url: "http://loki:3100/loki/api/v1/push"
        loki-external-labels: "service=api-gateway,env=prod"
        mode: "non-blocking"      # не блокировать контейнер, если Loki недоступен
        max-size: "10m"           # буфер на диске на случай недоступности Loki
    networks: [observability]

  user-service:
    build: ./services/user-service
    logging:
      driver: loki
      options:
        loki-url: "http://loki:3100/loki/api/v1/push"
        loki-external-labels: "service=user-service,env=prod"
        mode: "non-blocking"
        max-size: "10m"
    networks: [observability]

networks:
  observability:
```

`mode: non-blocking` критичен — без него, если Loki недоступен, контейнер может зависнуть на write в stdout.

## Ограничение, которое нужно понимать

Loki Docker Driver ставит **только статичные labels**, заданные в `loki-external-labels` (плюс немного метаданных контейнера). Он **не парсит** содержимое JSON-строки и не может динамически вынести `level` или `statusCode` из тела лога в label — это умеет только Promtail/Alloy с pipeline stages.

Значит план "labels = service, env, level, transport" из предыдущего сообщения в чистом виде с driver не сработает для `level`/`transport`. Практическое решение:

- **Labels (через driver):** только `service`, `env` — низкая кардинальность, статичны.
- **Остальное (`level`, `statusCode`, `traceId`, `transport` и т.д.)** — остаётся как поля JSON внутри лога, фильтруется в Grafana через LogQL `| json` на этапе запроса, а не через labels.

Это даже лучше соответствует ранней рекомендации не превращать высококардинальные поля в labels.

## Grafana: подключение и запросы

### Datasource (provisioning, опционально)

```yaml
# grafana/provisioning/datasources/loki.yaml
apiVersion: 1
datasources:
  - name: Loki
    type: loki
    url: http://loki:3100
    isDefault: true
```

Смонтировать в `grafana` сервис через volume, либо добавить вручную в UI: Connections → Data sources → Loki → URL `http://loki:3100`.

### Примеры LogQL

```logql
# все ошибки одного сервиса
{service="api-gateway"} | json | level="error"

# 5xx ответы
{service="api-gateway"} | json | statusCode >= 500

# сквозной трейс одного запроса через все сервисы
{env="prod"} | json | traceId="4bf92f3577b34da6a3ce929d0e0e4736"
```

Последний запрос — твоя цель "единый сбор": один `traceId`, проставленный в HTTP-интерцепторе и прокинутый в gRPC metadata, позволяет в Grafana увидеть весь путь запроса через все сервисы одним фильтром, без явного label на каждый сервис.

Совет: запрос без label-фильтра (`{} | json | traceId=...`) сканирует все стримы и может быть медленным — лучше всегда добавлять хотя бы `{env="prod"}`, чтобы сузить выборку до нужного окружения перед парсингом JSON.
