- Что такое кэш и зачем он нужен (снижение latency, снижение нагрузки на источник данных)
- Cache hit / cache miss, hit rate
- Trade-off: скорость доступа vs актуальность данных (свежесть)

Паттерны чтения/записи

- **Cache-Aside (Lazy Loading)** — приложение само читает/пишет в кэш
- **Read-Through** — кэш сам подгружает данные при промахе
- **Write-Through** — запись синхронно идёт и в кэш, и в БД
- **Write-Behind (Write-Back)** — запись сначала в кэш, потом асинхронно в БД
- **Write-Around** — запись мимо кэша, напрямую в БД

Уровни (где физически живёт кэш)

- Клиентский кэш (браузер, мобильное приложение)
- CDN / edge-кэш
- Кэш на уровне приложения (in-memory: локальный процесс)
- Распределённый кэш (Redis, Memcached)
- Кэш на уровне БД (query cache, buffer pool)
- Кэш на уровне ОС/диска

 Инвалидация и время жизни

- TTL (time-to-live), soft TTL vs hard TTL
- Event-based инвалидация (по событию изменения данных)
- Версионирование ключей (cache busting)
- «Самая сложная задача в CS» — почему инвалидация нетривиальна

Политики вытеснения (eviction policies)

- LRU (Least Recently Used)
- LFU (Least Frequently Used)
- FIFO
- Random Replacement
- ARC, TinyLFU (продвинутые алгоритмы)

Распределённое кэширование

- Consistent Hashing (для шардирования кэша)
- Репликация кэша (для отказоустойчивости)
- Cache coherence — согласованность между узлами
- Sticky sessions vs shared cache

Типичные проблемы (антипаттерны)

- **Cache Stampede / Thundering Herd** — массовые запросы при истечении одного ключа
- **Cache Avalanche** — массовое истечение TTL сразу у многих ключей
- **Cache Penetration** — запросы к несуществующим данным, кэш не спасает
- **Hot Key problem** — один ключ получает непропорционально много трафика
- Решения: request coalescing, jitter в TTL, bloom filter, locking

HTTP-кэширование (частный, но важный случай)

- Заголовки: Cache-Control, ETag, Last-Modified, Expires
- Проверка свежести: конditional requests (If-None-Match)

### 9. Инструменты

- Redis (структуры данных, персистентность, кластеризация)
- Memcached (чем отличается от Redis)
- CDN-провайдеры (Cloudflare, Fastly, CloudFront)

### 10. Метрики

- Hit ratio / miss ratio
- Latency p50/p95/p99
- Eviction rate, memory usage

## Ветка 2: Message Queue / Event Bus / Job Queue

### 1. Базовые понятия

- Асинхронная коммуникация vs синхронная
- Decoupling producer и consumer
- Термины: producer, consumer, broker, topic/queue, partition, offset

### 2. Модели обмена сообщениями

- **Point-to-Point (Queue)** — одно сообщение обрабатывается одним consumer'ом
- **Publish-Subscribe (Pub/Sub)** — сообщение получают все подписчики топика

### 3. Разновидности систем (важно различать!)

- **Message Queue** — обмен сообщениями/командами между сервисами
- **Job Queue / Task Queue** — постановка фоновых задач в очередь (Celery, Sidekiq, BullMQ)
- **Event Bus** — распространение событий по системе (event-driven architecture)
- **Event Streaming** — непрерывный поток событий (Kafka-стиль), в отличие от разовой доставки

### 4. Гарантии доставки

- At-most-once
- At-least-once
- Exactly-once (и почему это сложно достижимо технически)

### 5. Упорядочивание и партиционирование

- Ordering guarantees (в рамках партиции vs глобально)
- Partition key, как выбирается
- Consumer groups и параллелизм чтения

### 6. Надёжность обработки

- Idempotency обработчиков (критично при at-least-once)
- Retry policies, exponential backoff
- Dead Letter Queue (DLQ) — куда падают «ядовитые» сообщения
- Acknowledgment (ack/nack), visibility timeout

### 7. Масштабирование

- Горизонтальное масштабирование consumer'ов
- Партиционирование топика
- Backpressure — что делать, если consumer не успевает

### 8. Архитектурные паттерны (Event-Driven Architecture)

- Choreography vs Orchestration
- Saga pattern (распределённые транзакции)
- CQRS (Command Query Responsibility Segregation)
- Event Sourcing (хранение истории событий как источник истины)

### 9. Технологии/брокеры (и их отличия)

- RabbitMQ (AMQP, «умный брокер / глупый consumer»)
- Apache Kafka (распределённый лог, «глупый брокер / умный consumer»)
- AWS SQS (очередь) / SNS (pub-sub)
- Redis Streams / Redis Pub-Sub
- NATS, Google Pub/Sub

### 10. Типичные проблемы

- Дублирование сообщений
- Нарушение порядка доставки
- Poison messages (сообщения, которые всегда падают)
- Message loss

### 11. Мониторинг

- Consumer lag (насколько consumer отстаёт от producer)
- Глубина очереди (queue depth)
- Throughput, latency доставки

## Общая ветка-мост: где Cache и Message Queue пересекаются

- CAP-теорема: consistency vs availability в распределённых системах
- Latency vs throughput trade-offs
- Когда достаточно кэша, когда нужна очередь, а когда нужны оба вместе (например: событие меняет данные → инвалидация кэша через очередь событий)
