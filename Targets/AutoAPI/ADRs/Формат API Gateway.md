# ADR-004: Реализация API Gateway

**Статус:** Принято  

**Дата:** 2026

## Контекст

Система построена на микросервисной архитектуре с межсервисным взаимодействием по gRPC. Масштабирование и координация K8s, кеширование в Redis. Требуется единая точка входа для внешних клиентов и маршрутизация на внутренние микросервисы. 

Необходимо выбрать подходящий формат API Gateway, определить его область ответственности и способ реализации. 

## Решение 1: формат API Gateway

Реализовать thin API Gateway с конфигурационно-управляемой маршрутизацией: настройки задаются через внешний конфиг без изменения исходного кода, т.о. обработка бизнес-логики не попадает в исходный код API Gateway, новый микросервис или изменение upstream подключаются правкой конфига, а не деплоем новой версии API Gateway.   

Здесь может быть 2 подхода к настройке API Gateway: 

1. Конфигурирование только маршрутизации запросов на внутренние микросервисы. Проблема подхода заключается в том, что строго типизированные gRPC-ответы от микросервисов сложно однозначно преобразовать в корректные HTTP Envelope на стороне такого API Gateway. Это означает, что в данном случае логика по адаптации должна будет перетекать в микросервисы при том, что микросервисы, кроме прочего, не должны быть привязаны к текущей реализации API по взаимодействию с клиентами
2. Конфигурирование как маршрутизации, так и правил трансформации данных. Микросервисы остаются полностью agnostic к клиентскому API и возвращают только чистые Protobuf-сообщения в соответствии с gRPC-контрактами, а API Gateway остается thin-слоем, так как правила обработки Envelope меняются исключительно через обновление конфигурации без пересборки шлюза. Основная проблема данного решения в сложности конфигурации и необходимости либо в разработке DSL, либо в поиске оптимального формата конфига

Для реализации API Gateway выбран второй подход. 

## Причины

- Разделение ответственности: обработка бизнесс-логики только внутри соответствующих микросервисов, работа с внешним API только на стороне API Gateway без нарушения границ сервисов.
- Устранение необходимости в обновлении исходного кода API Gateway при каждом изменении системы и API в процессе разработки

## Последствия

- Config-driven маршрутизация: объявление в конфиге внешних эндпоинтов (версия API, method, headers, используемые path- и query-параметры), маршрутов (DNS-адрес микросервиса, метод, ссылка на Protobuf Descriptor, входные параметры вызываемых функций), правил генерации body, meta и headers
- Необходимость решения проблемы автоматической генерации документации для REST API с таким подходом

## Решение 2: реализация API Gateway

Реализовать API Gateway на NestJS вместо готовых NGINX, APISIX, Envoy, Kong, KrakenD, Traefik и других: подход позволяет использовать гибкость, расширяемость и готовые модули фреймворка для сборки thin API Gateway в виде, оптимальном с точки зрения домена, maintainability и минимизации operational complexity и infrastructure coupling. Выбор NestJS на начальном этапе целесообразен, поскольку приоритетом является построение тестируемой, прозрачной и расширяемой структуры API Gateway с явным разделением ответственности, а не достижение максимальной производительности с самого начала

## Причины

- Достижение свободы проектирования и реализации domain-first-подхода к разработке: с Envoy/Nginx и другими готовыми решениями инфраструктура в большей степени диктует правила реализации приложения, чем backend-фреймворк
- Попытки избежать преждевременной оптимизации: в активной фазе разработки на старте проекта более важно иметь высокую архитектурную гибкость, обеспечивать прозрачность и предсказуемость изменений
- NestJS одно из наиболее консистентных решений относительно текущего бэкенд-стека
- Максимизация тестируемости и maintainability
- Минимизация operational complexity и infrastructure coupling

## Последствия

- На данном этапе ответственность за масштабирование возлагается на k8s, внутренняя маршрутизация производится через DNS Kubernetes, таким образом шлюз не перегружается логикой отслеживания IP-адресов, являясь самостоятельной единицей масштабирования и позволяя инфраструктуре автоматически находить нужные поды и балансировать нагрузку между ними
- Решение оставляет возможность как вертикально масштабировать шлюз через настройку кластера и управление потоками в контейнере средствами node.js, так и горизонтально за счет внедрения Envoy для балансировки нагрузки на L7-уровне gRPC-стримов вместо kube-proxy





## Решение 3: итоговое разделение ответственности



1. **Балансировка нагрузки:** Round-robin, least connections, IP hash, health checks.
2. **TLS / mTLS termination:** Завершение шифрования на входе и перешифрование внутрь кластера.
3. **Статический контент и кэширование:** Отдача файлов, кэширование ответов upstream-сервисов.
4. **Базовый L7 роутинг:** Маршрутизация по путям (`location /api/`), заголовкам (`Host`, `User-Agent`) или методам HTTP.
5. **Защита backend-сервисов:** Буферизация запросов/ответов, таймауты, ограничение размера payload.
6. **Базовый Rate Limiting:** Ограничение запросов по IP или простому ключу (leaky bucket / token bucket).
7. **Манипуляция заголовками:** Добавление, удаление или перезапись HTTP-заголовков.
8. **Простое gRPC-проксирование:** Прозрачная передача gRPC-трафика (`grpc_pass`) без изменения payload.



Выбор стиля API Gateway 












**NestJS вместо Nginx** — кастомная логика аутентификации (revocation list, алгоритмы подписи) непрактична в Nginx без Lua или внешних auth-сервисов. NestJS разделяет стек с командой: общие типы, библиотеки, CI/CD.

**NestJS вместо Envoy сразу** — Envoy требует нетривиальной конфигурации xDS/control plane для динамической маршрутизации. На старте K8s + NestJS достаточно и проще в поддержке. Envoy не исключается — он добавляется поверх без изменений в gateway.



**DNS-based discovery** — привязка к DNS-именам сервисов внутри кластера даёт стандартный K8s-механизм без внедрения service registry (Consul, Eureka) на начальном этапе.

### Маршрутизация, TLS, mTLS

Когда клиент обращается по адресу `/api/v1/accounts/123`, кто-то должен решить — какой именно сервис обработает этот запрос. Маршрутизация — это таблица правил "этот URL → вот этот сервис". TLS — это HTTPS, шифрование соединения между клиентом и Gateway. mTLS — то же самое, но оба участника (Gateway и микросервис) предъявляют друг другу сертификат, то есть сервис тоже проверяет что запрос пришёл именно от Gateway, а не от кого-то постороннего.

---

### JWT валидация (подпись/expiry)

Клиент присылает токен — строку, которая говорит "я пользователь 123". Токен подписан секретным ключом. Gateway проверяет подпись (токен не подделан) и срок действия (токен не просрочен). Это чисто математическая проверка — Gateway не знает ничего о правах этого пользователя, только что токен валиден.

---

### Rate limit по IP/ключу

Если один клиент шлёт тысячу запросов в секунду — он может положить весь сервис. Gateway считает количество запросов от каждого IP или API-ключа и начинает отвечать `429 Too Many Requests` когда лимит превышен. Это как турникет на входе — пропускает не более N человек в минуту.

---

### Трассировка, логи, метрики

Трассировка — каждому запросу присваивается уникальный ID, который передаётся через все сервисы. Потом можно открыть Jaeger/Zipkin и увидеть весь путь запроса: сколько времени он провёл в каждом сервисе. Логи — структурированная запись каждого запроса и ответа (кто, куда, что, когда, сколько миллисекунд). Метрики — агрегированная статистика: средняя latency, количество ошибок в минуту, RPS — всё то что рисуется на дашборде в Grafana.

---

### Circuit breaker, retry, timeout

Если микросервис начал тормозить или падать — не нужно продолжать заваливать его запросами. Circuit breaker ("автоматический выключатель") следит за процентом ошибок, и когда он превышает порог — перестаёт отправлять запросы к этому сервису на некоторое время, сразу возвращая ошибку. Retry — если запрос упал по сетевой причине, попробовать ещё раз автоматически. Timeout — если сервис не ответил за N миллисекунд, не ждать вечно, вернуть ошибку.

---

### gRPC transcoding

Микросервисы общаются по gRPC — бинарный протокол поверх HTTP/2, быстрый и эффективный. Но браузер не умеет делать gRPC-запросы напрямую. Transcoding — это автоматический перевод: клиент шлёт обычный REST-запрос с JSON, Gateway конвертирует его в gRPC и отправляет сервису, получает gRPC-ответ и конвертирует обратно в JSON. Клиент вообще не знает что внутри gRPC.

---

### HTTP кэш по Cache-Control

Если клиент запросил данные аккаунта, и сервис ответил с заголовком `Cache-Control: max-age=300` — Gateway сохраняет ответ на 5 минут. Следующие запросы на тот же URL Gateway отвечает сам, не обращаясь к сервису вообще. Сервис контролирует сколько можно кэшировать через заголовки — Gateway просто исполняет.

---

### Security headers, CORS

Security headers — заголовки в HTTP-ответе которые говорят браузеру как вести себя: не выполнять inline-скрипты, всегда использовать HTTPS, не рендерить страницу во фрейме на другом домене. CORS — механизм браузера: когда фронтенд на `app.example.com` обращается к API на `api.example.com` — это cross-origin запрос. Gateway добавляет заголовки которые разрешают конкретным доменам делать такие запросы, иначе браузер заблокирует их сам.

---

### Балансировка нагрузки

Один микросервис обычно запущен в нескольких копиях (инстансах) чтобы выдержать нагрузку. Когда приходит запрос — нужно выбрать к какому инстансу его отправить. Round-robin — по очереди. Least connections — к тому у кого меньше активных запросов. Weighted — некоторые инстансы мощнее, им достаётся больше трафика. Gateway делает этот выбор незаметно для клиента.

---

### Бизнес-авторизация (RBAC/scopes)

JWT-валидация доказала что токен настоящий — но может ли этот конкретный пользователь читать чужой аккаунт? Это уже бизнес-вопрос. RBAC (Role-Based Access Control) — у пользователя есть роли (admin, manager, viewer), у каждой роли набор разрешений. Scopes — более гранулярно: токен может иметь право `accounts:read` но не `accounts:write`. Эта логика требует понимания доменной модели, поэтому относится к Fat Gateway.

---

### Агрегация нескольких сервисов

Клиенту нужна страница профиля: данные аккаунта + история транзакций + настройки уведомлений. Это три разных сервиса. Fat Gateway делает три запроса параллельно, ждёт все три ответа и склеивает их в один JSON который отдаёт клиенту. Без этого клиент был бы вынужден сам делать три отдельных запроса.

---

### Трансформация / фильтрация полей

Сервис возвращает объект аккаунта со всеми полями включая внутренние — `internal_flags`, `billing_id`, `audit_log`. Клиенту это не нужно и даже опасно отдавать. Fat Gateway фильтрует лишнее, переименовывает поля под соглашения фронтенда (`user_name` → `username`), преобразует форматы дат. Тонкий Gateway этого не делает — он не знает что "лишнее".

---

### BFF адаптация под клиент

BFF (Backend For Frontend) — паттерн когда для каждого типа клиента свой Gateway. Мобильному приложению нужен компактный ответ (медленный интернет, маленький экран). Веб-приложению нужно больше данных. Партнёрскому API нужен другой формат вообще. Вместо того чтобы один сервис пытался угодить всем — Fat Gateway адаптирует ответы под каждый тип клиента отдельно.

---

### Оркестрация (fan-out, join)

Иногда запросы к сервисам зависят друг от друга по цепочке: сначала получить ID аккаунта, потом по этому ID получить транзакции, потом по ID транзакций получить детали. Fat Gateway управляет этой последовательностью. Fan-out — разослать запрос сразу нескольким сервисам параллельно. Join — дождаться всех и объединить результаты. Это оркестрация в отличие от хореографии где сервисы сами договариваются между собой.

---

### Обогащение запросов

Клиент прислал запрос с JWT-токеном. Fat Gateway декодирует токен, достаёт из него `user_id`, `tenant_id`, `locale` и добавляет эти данные в запрос к сервису через заголовки или metadata. Сервис получает уже обогащённый запрос и не тратит время на самостоятельную работу с токеном. Также Gateway может сходить в feature-flag сервис и добавить к запросу какие A/B флаги активны для этого пользователя.

---

### Кэш с бизнес-инвалидацией

Тонкий Gateway кэширует по TTL — просто ждёт пока время выйдет. Но если аккаунт обновился прямо сейчас — кэш устарел, а TTL ещё не истёк. Fat Gateway подписывается на бизнес-события ("аккаунт обновлён") и инвалидирует нужные ключи немедленно. Это требует понимания доменной логики — что за событие, какие ключи оно делает устаревшими.

---

### Graceful degradation / fallback

Если один из сервисов упал — не обязательно возвращать ошибку целиком. Fat Gateway может вернуть частичный ответ: данные аккаунта есть, история транзакций недоступна — вернём ответ без неё, с пометкой что раздел временно недоступен. Или вернуть закэшированные устаревшие данные с предупреждением. Тонкий Gateway не знает что является "частью" ответа — это бизнес-решение.

---

### Формирование ошибок под клиента

Сервис вернул `FAILED_PRECONDITION: acc_suspended_billing_overdue`. Fat Gateway переводит это в человекочитаемый ответ под конкретный клиент: мобильному — короткое сообщение и код для диплинка на экран оплаты, веб-клиенту — развёрнутый текст со ссылкой, партнёрскому API — машиночитаемый код `ACCOUNT_SUSPENDED` с документацией. Один и тот же домен-уровень ошибки — разная презентация.

---

### GraphQL / API composition

GraphQL — язык запросов где клиент сам описывает какие именно поля ему нужны. Fat Gateway может предоставить единую GraphQL-схему которая внутри обращается к десяткам gRPC-сервисов. Клиент пишет один запрос, получает ровно те поля что просил — без over-fetching (лишних данных) и under-fetching (нехватки данных). Это предельный случай агрегации и трансформации — поэтому только Fat Gateway.


### Тонкий Gateway (Thin / Infrastructure Gateway)

**Область ответственности:** инфраструктурный прокси, прозрачен для бизнес-логики

**Задачи:**

**Маршрутизация**

- Маршрутизация запросов по URL, методу, заголовкам
- Версионирование API (`/v1/`, `/v2/`)
- Canary / Blue-Green routing по весам
- Маршрутизация по тенанту / региону

**Безопасность**

- TLS терминация
- Проверка JWT / API-ключа (валидность подписи, expiry) — без бизнес-авторизации
- mTLS между Gateway и сервисами
- CORS заголовки
- Защита от DDoS (connection limits, request size limits)
- IP allowlist / blocklist
- Basic rate limiting по IP или API-ключу

**Наблюдаемость**

- Structured logging запросов и ответов
- Распределённая трассировка (создание root span, передача trace-id)
- Метрики: latency, RPS, error rate
- Health check эндпоинты (`/health`, `/ready`)

**Протокол**

- gRPC-transcoding (gRPC → REST для веб-клиентов)
- Маппинг gRPC Status → HTTP Status (fallback)
- WebSocket проксирование
- HTTP/1.1 → HTTP/2 апгрейд

**Сеть**

- Балансировка нагрузки между инстансами сервиса
- Circuit breaker (открыть цепь если сервис недоступен)
- Retry с backoff для идемпотентных запросов
- Timeout enforcement
- Connection pooling к upstream сервисам

**Кэширование**

- HTTP-кэш GET-ответов по Cache-Control от сервиса
- 304 Not Modified по ETag
- Stale-while-revalidate

**Заголовки**

- Добавление `X-Correlation-Id`, `X-Request-Id`, `X-Trace-Id`
- Добавление `X-Response-Time`
- HSTS, security headers
- Удаление внутренних заголовков перед отдачей клиенту

### Толстый Gateway / BFF (Fat Gateway)

**Область ответственности:** бизнес-оркестратор, адаптер под конкретный клиент

Включает **все задачи тонкого** + следующие:

**Агрегация и оркестрация**

- Вызов нескольких сервисов и склейка ответов в один
- Последовательная оркестрация (результат одного сервиса → вход другого)
- Параллельные fan-out запросы с join результатов
- Partial response — вернуть что успело если часть сервисов упала

**Трансформация данных**

- Переименование, маппинг, фильтрация полей ответа
- Конвертация форматов (XML → JSON, Protobuf → JSON)
- Формирование структуры ответа под конкретный клиент (mobile vs desktop)
- Удаление чувствительных полей перед отдачей клиенту

**Бизнес-авторизация**

- Проверка прав доступа к конкретному ресурсу (не только "токен валиден")
- Scope-based authorization
- Row-level security (может ли этот пользователь читать этот аккаунт)

**Адаптация под клиент (BFF)**

- Отдельные эндпоинты для mobile / web / partner API
- Подбор размера payload под bandwidth клиента
- GraphQL слой поверх REST/gRPC сервисов

**Кэширование с бизнес-логикой**

- Кэш с осведомлённостью о правах пользователя
- Инвалидация кэша по бизнес-событиям
- Персонализированные кэш-ключи (per-user, per-role)

**Обогащение запросов**

- Добавление данных из профиля пользователя к запросу
- Локализация / i18n на уровне gateway
- A/B тест флаги из feature-flag сервиса

**Обработка ошибок**

- Формирование понятных клиенту ошибок из технических ответов сервисов
- Fallback данные если сервис недоступен
- Graceful degradation — вернуть частичный ответ вместо ошибки
